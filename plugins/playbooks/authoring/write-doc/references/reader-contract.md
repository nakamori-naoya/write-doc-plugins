# 工程間で引き継ぐ記録

**資料は、誰か一人のために書く。** その一人を先に決め、読後の到達点を固定してから型を選び、到達点の問いに本文だけで答えられるかを確かめる。工程の状態には次の記録のpathを登録し、本文へ管理用の表を挿入しない。

記録の置き場は、実行の最初に `ARTIFACT_DIR=$(mktemp -d)` で作る一時 directory である。作業repositoryの中には作らず、後始末は write-doc が行う。各記録は `$ARTIFACT_DIR/<記録名>.md`（YAMLの記録は `.yml`）に置く。

## reader が作る記録

| 記録 | 内容 |
|---|---|
| `persona` | 同梱5人（[personas](../../../../skills/authoring/content-types/references/personas.md)）から選んだ1人のファイルpath |
| `reader_context` | 案件固有の語の知識段階（実務で使える／言われれば分かる／知らない）、読む場面、起こりそうな誤解、到達点、下の4項目。根拠がない前提は仮定と記す |
| `goal_questions` | 読み手が読後にできるべき判断・行動を、本文だけを読んだ人が答えられる問い2〜4個にしたもの。1個では判断か行動の片方しか照合できず、5個以上は到達点が複数ある印である。各問いに `expected`（期待する答え）を添え、draft 工程が本文と照合する |
| `open_questions` | 読み手または到達点が依頼から決まらないこと、および到達点の判断に必要な事実で素材に無いもの。先頭に `count: <件数>`。各問いは `id`（`[A-Za-z0-9._-]` のみ）、問い、推奨回答、答えで何が変わるかを持つ。型の節を埋められないこと、依頼が明示している事項、調べれば分かることは含めない |
| `type`、`template` | 選んだ型のslugとテンプレートのpath |

`reader_context` の4項目。書き手と読み手は前提も経緯も共有しない、を既定にする。

| 項目 | 何を書くか |
|---|---|
| `premises` | 主張が成り立つ条件のうち、読み手が知らないもの。素材の経緯から条件だけを取り出す。無ければ「前提は共有しない」 |
| `stance` | 主張への読み手の初期態度。`初耳` / `賛成` / `反対` / `別案を持つ`。既定は `初耳` |
| `history` | 経緯の扱い。`時系列で残す` / `前提へ畳む` / `書かない`。型が決まった直後に content-types が、カタログ「経緯の扱い」の型既定を写す。型の無い単独使用では `書かない` |
| `verification_means` | 読み手が根拠を確かめる手段。ペルソナから決める（pm-3 は数字、backend-5 はコードと再現手順）。既定は「リンクを開く」 |

読み手の言語は writing-rules の `style` に従う。判定に使うのはペルソナの3段階だけで、「日本人」「エンジニア」という属性から分野固有の知識を仮定しない。複数の読み手がいる場合も、本文が支える到達点は一人ぶんに決める。別の専門性や目的が必要な詳細は分離候補として記録し、別文書の作成は依頼範囲に含まれる場合だけ行う。

## settle が作る記録

| 記録 | 内容 |
|---|---|
| `decisions` | grill が `output_to` へ書いた YAML（決定と未決）を `$ARTIFACT_DIR/decisions.yml` へ写した絶対 path |

`open_questions.count > 0` のときだけ `settle` 工程が動く。問いが無ければ `state.py skip --step settle` で飛ばし、`decisions` は作らない。draft は未決として残った項目を仮定にせず、本文で未確認と明示する。

## draft が作る記録

| 記録 | 内容 |
|---|---|
| `body` | 本文の Markdown ファイルの絶対 path。強調の役は[役の契約](roles.md)の印で囲んである。図は含めず、挿入位置は `visual` 工程が `figures_applied` で返す |
| `roles_applied` | `body` で使った役の名前のカンマ区切り（`要点,キーワード`）。使っていなければ `none`。save は `none` のとき本文に印が無いことを確かめる |
| `reading_path` | 到達点に必要な概念を、足場・導入する節・初めて使う節・図とともに並べた経路表（writing-rules の `path`）。本文の順序と長さはこの表で決まり、表に無い節は本文に置かない。テンプレートの節を省略・統合・並べ替えた理由もここに残す |
| `reader_review` | writing-rules の final-check に沿って、問い、本文だけから導ける答え、その根拠の節、修正した箇所、残る未確認を記した記録。文書の主張1文と決定的根拠の所在も残す |

`reader_review` は自己申告であり、機械の合否ではない。draft 工程は `goal_questions` の各問いに本文だけで答えられるかを自分で照合し、答えられない問いや詰まりが残るなら、表現ではなく経路表の概念の順序と足場から直してから `save` へ渡す。別の読み手役を起こして再検証させる工程は置かない。

## visual と save が作る記録

| 記録 | 内容 |
|---|---|
| `figures_applied` | `$ARTIFACT_DIR/figures-applied.yml`。形は下のとおり。0枚なら `count: 0` と `reason` |
| `path` | 保存した資料の絶対 path（`write-doc.sh` が返した値） |

```yaml
count: <採った図の数>
reason: <0枚のときだけ。図にすると理解が速くなる関係が無い理由>
figures:
  - claim: <図の主張>
    type: <図の型>
    kind: mermaid | image
    content: <Mermaid のコード。image なら実ファイルの絶対 path>
    insert_after: <本文で図を置く直前の段落の先頭20文字>
```

`kind: image` の図は `content` が実在するファイルでなければならない。無ければ visual 工程を fail にする（[図の要件](figures.md)）。

## 工程を差し替える場合

利用者が `steps` を差し替える場合も、読み手を一人決めること、到達点を問いへ落とすことの2つを残す。既定のartifact名を変えた場合は対応する needs/provides も揃える。
