# 引くための型

手順書やコンセプトが「教育・情報提供」を扱うのに対し、リファレンスは**原因と結果**——行動とその結果——を扱う。

## APIリファレンス

**読み手**: 実装中の開発者
**目的**: 値と仕様を正確に引かせる
**成功条件**: すべてのリソース・エンドポイントが引け、例とエラーが揃っている

開発が始まると、ユーザーはリファレンスに頼り切る。**サービスのコードに根ざした真の情報源**として機能させる。

良いリファレンスの条件。

- すべてのリソースとエンドポイントの詳細がある
- **豊富な例**がある
- ステータスコードとエラーメッセージが定義され、一覧になっている

**簡潔で最小限にする。** 準拠する仕様（REST / JSON など）と認証方法を先に共有してから各論へ入る。

包括的に保つ最良の方法は、**ソースコードのコメントから自動生成する**こと。手作業のページを減らし、コードと内容を結合できる。

## 用語集

**読み手**: 全員
**目的**: 用語を**1つの意味に固定する**
**成功条件**: 同じ語が別の意味で使われていない

どんな複雑なシステムにも意味が不明瞭な用語がある。**用語の不統一は、読み手の理解を妨げるだけでなく、提供側が定義に確信を持っていないことを示し、信頼を下げる。**

包括的である必要はないが、**サービスを使うのに必要な用語は定義されていること。**

外部リンクは制限する。サードパーティーが情報を最新に保ち同じ場所に置き続けることを期待することになり、彼らに振り回される。

## トラブルシューティング

**読み手**: 困っている人。**急いでいる**
**目的**: 症状から原因と復旧へ最短で導く
**成功条件**: **症状で引ける**こと。原因の切り分けが分岐で書かれていること

サービスのギャップや制約は、開発者が直すより先にユーザーが見つけることが多い。既知の問題が特定できたら、ここに書いて次の人を救う。

**既知の未解決を隠さない。**

## Runbook（運用手順書）

**読み手**: 運用者。正確さが要る
**目的**: **誰がやっても同じ結果**にする
**成功条件**: 判断の余地が無く、失敗時の戻し方がある

ハウツーガイドとの違いは、**反復と正確性**にある。「状況に応じて判断」と書いた時点で Runbook としては失敗しており、分岐を明示するか、ハウツーへ格下げする。

**テンプレート**: [`assets/templates/runbook.md`](../../assets/templates/runbook.md)
