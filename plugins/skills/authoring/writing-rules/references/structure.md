# 構成ガイド（既定）

文書全体で、読み手が何をどの順に理解するかを決める。差し替える場合は `.harness-plugins/writing-rules.config.yml` の `rules.structure` に自分のファイルを指す。

## 到達点へ至る順序を選ぶ

最初に、読み手が解きたい問いと、この文書が答える範囲を示す。読み手がすでに知っていることは足場に使い、新しい概念は用途や既知のものとの関係を添えて導入する。著者が調べた順序や実装の階層を、そのまま説明順序にしない。

概念や設計を理解する資料では、対象の目的、主要な要素、その関係から全体像を作ると詳細を位置づけやすい。全体像は箱の列挙だけでなく、何が何に作用し、どこまでを扱うかを伝える。読者が対象を想像できない場合は短い具体的な場面から始め、その場面を説明する全体像へ進めてもよい。

構成は読者の目的で選ぶ。たとえば、障害対応なら症状から切り分けへ、操作なら開始条件から操作と成功確認へ、判断依頼なら求める判断と判断根拠へ進む。専門家が項目を探す参照資料では、検索しやすい分類と条件の明示を優先する。すべての文書を「要約→全体像→概要表→詳細」に揃えない。

各節の入口で、その節が何を明らかにし、前の説明とどうつながるかが分かるようにする。後の節で前提・用語・粒度が変わるなら、その変化を伝える。冒頭を単純化するときも、判断を覆す条件を後半まで隠して誤った理解を作らない。

## 本文に残す情報を選ぶ

読後の判断・行動に必要な情報と、それを誤らせない条件を本文に残す。重要な例外・限界・未確認は、影響する主張の近くに示す。

別の専門性を要する実装詳細、主目的に影響しない派生論点、網羅的な記録は、付録・既存の参照先・別文書への分離を検討する。主張の根拠まで追い出して、リンクを開かなければ筋が分からない本文にしない。別文書を作る場合は依頼の範囲内で行い、未作成のものを完成済みのリンクとして載せない。

同じ深さの節でも、説明量は読み手の難所に合わせる。粒度を揃えるために既知の事項を膨らませたり、難しい関係を省略したりしない。

## 要約・図・表は理解の用途で置く

要約は、読む価値、答えの見通し、求める判断を短く伝える必要があるときに置く。本文を読まなくても結論の条件を誤解しない形にする。末尾の総括は、複数の説明を統合して判断へ結びつけるときに使い、冒頭の反復になるなら省く。長さだけで両方を強制しない。

図は関係や流れ、表は共通の軸による比較・対応、文章は理由や因果の展開に使う。概要表、箇条書き、図を置いたこと自体を全体像の説明とみなさない。
