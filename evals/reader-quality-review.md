# write-docの読者理解を基準にした改修

## 目指す品質

読み手が、文書を読む目的に必要な理解を本文から組み立て、その理解を使って説明・判断・行動できることを目指す。既知のことと新しいことの関係がつながり、何が言えて何がまだ言えないかを区別できる文書にする。

この基準から、情報の取捨選択、説明順、詳しさ、例や図の必要性を選ぶ。全体像から詳細へ進む構成や抽象と具体の往復は有効な方法の例であり、すべての文書に適用する形式ではない。

## 依頼との対応と根拠

依頼時の画像は、倉島保美『改訂新版 書く技術・伝える技術』として「そのモデルを壊さぬように文章を展開しなければなりません」と述べている。確認した書籍本文はこの提供画像の範囲に限る。ここから、読み手が築いた理解を説明の途中で唐突に覆さないという方針を採った。書籍全体の手法を再現したとは扱わない。

読者の前提・到達点を工程間で渡す方法や、本文から問いに答えて確認する方法は、このプラグイン向けに設計したものである。読み手の既存の理解が誤っている場合は、誤解を温存せず、修正する関係と理由を明示する。

ユーザーが良い例として挙げた業務文書とデータモデル文書は、以下の点を読み取る参考にした。両文書のテンプレート・記載例は変更していない。

- [業務文書](../plugins/skills/authoring/content-types/assets/templates/domain-rule.md)は、業務の決まりと最後の具体例を対応させ、書く対象を業務知識へ限定している。
- [データモデル文書](../plugins/skills/authoring/content-types/assets/examples/rdb-logical-data-modeling.example.md)は、業務シナリオ、残す事実、モデル、記録の変化を結びつけている。

## 何が変わったか

型を決めるだけでは、読み手の前提が執筆へ引き継がれなかった。既定playbookに`reader_context`と`reader_review`を追加した。前者は読む場面と既知・未知・誤解・到達点、後者は本文から試した問い・答え・根拠・修正・未確認の記録である。

テンプレートも、依頼や専門型で必要な見出し・順序を保ち、それ以外は目的に応じて省略・統合・並べ替えできるようにした。必須項目の情報不足は隠さない。

既存の文字数・段落数・表への分割などの一律規則は、理解のまとまりを見直す目安へ変更した。強調がないという理由だけで、必要な前提や具体例を削らないようにした。図の最低枚数は既定では要求せず、明示的な必須指定は保持した。

## 読解ウォークスルー

以下は同じ執筆者が作成・確認した説明用の例である。外部の読者テストや独立モデルによる生成比較ではない。題材の仕様はこの評価用に固定した架空の条件であり、実在サービスの事実ではない。

### ケース1: 申請者が「提出」と「承認」を混同している

入力条件: 申請者はフォームを送った時点で備品を買えると思っている。実際には提出は審査待ちで、承認の通知後に購入できる。10万円以上は部長承認が追加で必要。本文の目的は今購入してよいか判断すること。監査ログの保存方式は今回不要。

不良例:

> 申請はsubmitted、approvedの状態で管理する。10万円以上には追加フローがある。監査ログはイベントごとに保存する。詳細は承認仕様を参照。

改善例:

> フォームを提出しただけでは、まだ備品を購入できない。提出は審査の受付であり、必要な承認がそろった通知を受けてから購入できる。
>
> たとえば8万円の椅子を申請して「提出済み」と表示された場合は、承認通知を待つ。10万円以上の申請には部長承認も必要なので、上司だけが承認していても購入を待つ。
>
> 金額に応じた承認がすべてそろったかを確認すれば、購入してよいかを判断できる。監査ログの保存方式は、この判断には関係しないため本書では扱わない。

| 試す問い | 本文からの答えと根拠 |
|---|---|
| 8万円で「提出済み」。買ってよいか | まだ購入できない。冒頭で提出を審査の受付と定義している |
| 例とは違う12万円で、上司だけ承認。買ってよいか | 部長承認も必要なので待つ。金額条件を本文へ残している |
| ちょうど10万円ならどうか | 「10万円以上」なので部長承認が必要。条件の境界も本文から判定できる |
| 承認が何日で終わるか | 本文からは分からない。所要日数を推測しない |

不良例では状態名の定義と購入可否の関係を読み手が補う必要がある。改善例では、その誤解を最初に修正し、金額条件を変えても判断できる。

### ケース2: 操作を知っている当番が、処理結果の不明な再実行を判断する

入力条件: CSV取込の当番は画面操作を知っている。画面の待機が切れてもサーバーの取込が完了していることがある。取込IDで結果を確認し、「完了」なら再実行しない。「失敗」なら同じIDで再試行できる。「処理中」または照会不能なら再実行せず担当者へ連絡する。キューやロックの内部方式は別の専門資料の範囲。

不良例:

> 取込システムは画面、キュー、ワーカー、DBから構成される。ワーカーは非同期で実行される。タイムアウト時は状況に応じて再試行する。

改善例:

> 画面がタイムアウトしたら、再実行の前に取込IDで結果を確認する。画面の待機終了は、サーバーでの取込失敗を意味しない。
>
> 結果が「完了」なら再実行しない。「失敗」なら同じ取込IDで再試行する。「処理中」または結果を照会できない場合は再実行せず、取込IDを添えて担当者へ連絡する。

| 試す問い | 本文からの答えと根拠 |
|---|---|
| タイムアウト後、何を最初にするか | 取込IDで結果を確認する。最初の文に操作がある |
| 結果が「完了」なのに画面はタイムアウトした。再実行するか | しない。画面の待機とサーバーの結果を区別している |
| 結果の照会自体ができない。失敗とみなせるか | みなせない。再実行せず連絡する条件が明示されている |
| キュー内部の説明がなくても操作できるか | できる。必要なのは結果ごとの行動であり、内部方式ではない |

この例は全体像・具体例・末尾総括を追加していない。操作を知る読み手には、症状と条件分岐から入るほうが目的に直結する。

### ケース3: 同梱の概念文書を読む

[仮押さえ予約と確定予約](../plugins/skills/authoring/content-types/assets/examples/concept.example.md)では、10時に仮押さえした同じ予約を追い、期限前に確定した場合と確定しなかった場合を対応させた。

- 10時10分に確定した予約は10時15分を過ぎても残る。15分を会議室の利用時間とは解釈しない。
- 別の時刻である11時に仮押さえした場合も、確定猶予は11時15分までと判断できる。
- 期限時刻ちょうどの確定は受け付けない。この条件を別資料に隠していない。
- 15分の妥当性を実測した証拠はない。説明例を効果検証に読み替えない。

## 逆効果になる適用を避けられるか

| 逆効果 | 見直し後の判断 |
|---|---|
| 読者の誤解を壊さないため「提出したら購入可」に合わせる | 誤解を明示して修正する。正しさを犠牲にしない |
| どの文書も概要図から始める | ケース2では必要な操作から始める。図は追加しない |
| 全節へBDDや具体例を足す | 理解の飛躍がない手順・参照箇所には追加しない |
| 10万円以上の条件を枝葉として外す | 判断を変える条件なので本文に残す |
| 枝葉を分けるため未作成の運用資料へリンクする | 実在しないリンクは書かない。分離候補は作業記録へ残す |
| 強調する主張がないので必要な前提を削る | 理解に必要かで判断する |
| 例からすべての条件を推測する | 示した範囲と未確認を区別する |

## 確認の限界

工程間の引き継ぎは自動テストで確認するが、文章の意味や実際の読み手の理解を機械的に保証しない。上記は自己レビューである。独立モデル評価用のケースは`evals/reader-quality.json`へ残す。既存評価器のClaude CLIは認証がないため、このセッションでは独立モデル評価を実行していない。
