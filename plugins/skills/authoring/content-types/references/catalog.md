# コンテンツタイプのカタログ

**型は読み手と目的の宣言である。1つの型は、1人の読み手の1つの問いに答える。型は19種である。** 読み手の問いが同じなら同じ型で書き、1本に複数の型を混ぜない。混ぜるなら分けて相互リンクする。

読み手の目的で型を分けるという考え方と、README／ハウツーガイド／コンセプトドキュメント／トラブルシューティングの名称は、『エンジニアのためのドキュメントライティング ユーザーの問題解決とプロダクトの成功を導く』（ジャレッド・バーディ ほか著／岩瀬義昌 訳／[日本能率協会マネジメントセンター](https://pub.jmam.co.jp/book/b622627.html)／2023年3月／ISBN 978-4-8005-9083-1、原書 *Docs for Developers*）から借りている。**逐語の引用は含まない。**

## 選び方

**上から順に判定し、最初に当たった型を選ぶ。** 期間ダイジェストを最初に判定する。

```
0. 読み手は「この期間に何があったか」を追いたいか → 期間ダイジェスト
1. 読み手はプロダクトの方向または経路を決めたいか
     長期の価値ある未来と判断基準を揃えたい → Product North Star
     現在地から課題、方針、行動を選びたい   → Product Strategy
2. 読み手は業務の決まりを扱いたいか
     「業務として何が正しいか」を確定したい                  → 業務知識・コアドメイン
     確定した決まりを、要素と操作の契約へ割り当てて共有したい → ドメインモデル
3. 読み手は「複数の意味ある場面を通じてユーザーが目的を達成するまで」を共有したいか
                                                   → ユーザー目的達成BDD
4. 読み手は「業務のデータをどう永続化するか」を決めたいか
     業務シナリオからRDBへ記録する事実と論理構造を決めたい → RDB論理設計
     固定済みの論理構造を対象RDBへ写したい                → RDB物理設計
5. 読み手はシステム設計の根拠を扱いたいか
     誰の何をなぜ実現し、どこまでを対象にするかを根拠状態付きで共有したい → 要求発見正本
     利用者・操作・イベントごとの規模・分布・ピーク・増加・偏りを共有したい → 利用・負荷モデル
     業務影響を観測点・指標・閾値・時間窓・検証方法へ落としたい → 品質要求正本
     要求・負荷・品質・制約から将来のクラウド構成を比較・選定したい → クラウドアーキテクチャ
6. 読み手は「いま何がどこで動き、何と通信し、どこに何が残るか」を知りたいか → システム構成
7. 対象は、すでに存在する特定の変更（PR）か → 実装解説（PR）
8. 不具合の症状から原因・対処を切り分けたいか → トラブルシューティング
9. これから何をするかの一つの選択と判断根拠を残したいか → ADR
10. 既知の操作目的を達成したいか      → ハウツーガイド
11. 対象の意味・関係・働きを理解したいか → コンセプトドキュメント
12. リポジトリの入口か               → README
```

7番と9番は、対象がすでに在るかどうかで分かれる。「このPRを取り込んでよいか」は7番で、書かれた変更を説明する。「この方式を採るか」は9番で、まだ書かれていない。

2番は、作る前から在って作りが変わっても変わらない業務そのものを残す型である。実現手段が1文でも混ざったら、それは別の型の内容である。

どれにも当たらない場合だけ、設定の `default_type` を選ぶ。

## 一覧

| 型 | slug | 読み手 | 読み手の状態 | 目的 | 詳細 |
|---|---|---|---|---|---|
| **Product North Star** | `north-star` | 長期のプロダクト判断を揃える人 | 機能や指標はあるが、誰にどんな未来を実現するかが揺れている | 価値ある未来、判断原則、やらないことを定める | [detail/product.md](detail/product.md) |
| **Product Strategy** | `strategy` | 資源配分と行動を決める人 | North Starはあるが、現在地から何へ集中するかが決まっていない | 診断、基本方針、一貫した行動の因果を結ぶ | [detail/product.md](detail/product.md) |
| **業務知識・コアドメイン** | `domain-rule` | 業務を知る人と、それを形にする人 | 決まりが人によって違って伝わっている | 業務として何が正しいかを確定させる | [detail/domain.md](detail/domain.md) |
| **ドメインモデル** | `domain-model` | 業務を形にするエンジニア | 業務の決まりは確定したが、何を要素にし、何がどの操作をどんな契約で行うかが人によって違う | 業務概念を値オブジェクト・エンティティ・集約・ドメインイベントへ割り当て、目的・境界・不変条件・操作の契約を共通理解にする | [detail/domain.md](detail/domain.md) |
| **ユーザー目的達成BDD** | `user-journey-bdd` | ユーザーの目的達成を共通理解にする人 | 個々の振る舞いは分かるが、開始から観測可能な完了までが一続きに説明できない | 判定済みUser Journeyの目的、開始地点、意味ある場面、状態接続、最終地点をBDDで一続きにする | [detail/user-journey-bdd.md](detail/user-journey-bdd.md) |
| **RDB論理設計** | `rdb-logical-data-modeling` | 業務を知る人と、RDBへデータを永続化する人 | 何を記録すべきか説明できない | CUDの業務シナリオから記録する事実と論理構造を決める | [detail/data-modeling.md](detail/data-modeling.md) |
| **RDB物理設計** | `rdb-physical-design` | DB設計者・実装者・運用者 | 論理構造は決まったが対象RDBでの実現が決まっていない | 論理構造を変えず対象製品・版へ写す | [detail/data-modeling.md](detail/data-modeling.md) |
| **要求発見正本** | `requirements-discovery` | 何を作るか合意するプロダクト責任者と設計者 | 要求、仮説、設計案が混ざり、根拠と未決が追えない | 目的、受益者、観測可能な結果、範囲、境界、制約を根拠状態付きで共有する | [detail/system-design.md](detail/system-design.md) |
| **利用・負荷モデル** | `workload-model` | 容量と方式の前提を判断する設計者・運用者 | 平均値だけがあり、分布、ピーク、増加、偏りの根拠が追えない | 利用者・操作・イベントごとの利用・負荷特性を単位・時間窓・母集団・根拠付きで共有する | [detail/system-design.md](detail/system-design.md) |
| **品質要求正本** | `quality-requirements` | 品質の優先順位と検証を合意する責任者・設計者 | 「高速」「高可用」のような測定不能な表現しかない | 品質を観測点、指標、閾値、時間窓、対象母集団、検証方法へ落とす | [detail/system-design.md](detail/system-design.md) |
| **クラウドアーキテクチャ** | `cloud-architecture` | 将来構成を選び実装・運用判断へ渡す設計者 | プロバイダーやサービス名はあるが要求・負荷・品質との根拠が追えない | 将来のクラウド構成を比較・選定し、ADR、要求追跡、障害および縮退経路、編集可能な図を残す | [detail/system-design.md](detail/system-design.md) |
| **システム構成** | `architecture` | そのシステムを変更・運用するエンジニア | 何がどこで動き、何と通信し、どこに何が残るか分からない | 現在の構成（要素・通信・データの置き場・環境・制約）を照合できる名前で宣言する | [detail/architecture.md](detail/architecture.md) |
| **README** | `readme` | リポジトリに来た人 | これが何か分からない | 全体像と最初の一歩を渡す | [detail/code-and-repo.md](detail/code-and-repo.md) |
| **ハウツーガイド** | `how-to` | 目的が明確な人 | 手段を知らない | その課題だけを解決させる | [detail/learning.md](detail/learning.md) |
| **コンセプトドキュメント** | `concept` | 理解したい人 | 対象の意味や関係がつながっていない | 関係と適用範囲を理解し、場面に応じて判断できるようにする | [detail/learning.md](detail/learning.md) |
| **トラブルシューティング** | `troubleshooting` | 困っている人 | 症状しか分からない。急いでいる | 症状から原因と復旧へ最短で導く | [detail/reference.md](detail/reference.md) |
| **ADR** | `adr` | 将来の自分と後任 | なぜこの構成なのか分からない | 決定と、その時の文脈を残す | [detail/decision.md](detail/decision.md) |
| **期間ダイジェスト** | `period-digest` | 期間の動きを追う人 | その期間に何があったか分からない | 1枚で次の会に出られるようにする | [detail/tracking.md](detail/tracking.md) |
| **実装解説（PR）** | `pr-walkthrough` | レビュアー・後任 | 差分は見えるが、意味が読めない | 読ませる層のコードに注釈を振り、変更を分からせる | [detail/code-and-repo.md](detail/code-and-repo.md) |

型が決まったら、その詳細ファイルとテンプレート・記載例だけを読む。

## 型ごとに固定すること

### 固定見出しを持つ型

次の型では、見出しが型の不変条件である。`# 概要` のような役割名の見出しも残す。ここに無い型では、テンプレートの見出しは問いの候補であり、主張へ書き換え、経路に無い節は落とす。固定するのは見出しと順序だけで、節の中の小見出しと項目の数はペルソナと到達点から決める。固定見出しの節に該当が無ければ「なし」と書き、節を削らない。読み手が毎回同じ場所を見に行けるようにするためで、「該当が無かった」と「欄が無い」は別の情報である。

| 型 | 固定される見出し |
|---|---|
| 業務知識・コアドメイン | `# 概要`から`# BDD`までの全H1見出しと、その順序 |
| ドメインモデル | `## 目的と範囲`から`## この資料に書かないもの`までの全H2見出しと、その順序。モデル図は集約ごとに1枚の、公開コマンドだけのclassDiagram（集約が2つ以上なら「集約どうしの関係」も）。要素の数と、要素ごとの操作の数は固定しない |
| ユーザー目的達成BDD | `# Journey概要`、`# 場面`、`# 既知の分岐`、`# まだ決まっていないこと` |
| RDB論理設計 | `## リソース系とイベント系`から`## BDD`までの全H2見出しと、その順序 |
| RDB物理設計 | `## 対象と論理設計`以降の全H2見出しと、その順序 |
| システム構成 | `## 目的と範囲`から`## この資料に書かないもの`までの全H2見出しと、その順序 |
| 要求発見正本 | `## 状態と引き継ぎ`から`## この資料に書かないもの`までの全H2見出しと、その順序 |
| 利用・負荷モデル | `## 状態と引き継ぎ`から`## この資料に書かないもの`までの全H2見出しと、その順序 |
| 品質要求正本 | `## 状態と引き継ぎ`から`## この資料に書かないもの`までの全H2見出しと、その順序 |
| クラウドアーキテクチャ | `## 状態と引き継ぎ`から`## この資料に書かないもの`までの全H2見出しと、その順序 |
| Product North Star | `## 対象`から`## 未決`までの全H2見出しと、その順序。節の中の小見出しの数は固定しない |
| Product Strategy | `## 診断`、`## 基本方針`、`## 一貫した行動`と、その順序。行動の個数は固定しない |
| 実装解説（PR） | `## ① 処理の流れ`から`## ⑤ 気になった点`までの丸数字見出し |
| 期間ダイジェスト | `## 決まったこと`から`## 素材`までの全H2見出しと、その順序 |
| README | `## インストール`から`## もっと詳しく`までの全H2見出しと、その順序 |
| ハウツーガイド | `## 始める前に`から`## 関連`までの全H2見出しと、その順序 |
| トラブルシューティング | `## 症状から探す`、`## それでも直らないとき`、`## 既知の未解決`と、その順序。症状ごとの見出しは固定しない |

### 固定図を持つ型

次の型は、図がテンプレートの一部として固定されている。図の主張・型・内容はテンプレートの SVG が決め、図の工程は選び直さない。書き手はテンプレートの SVG を `<資料名>.assets/<テンプレートのファイル名>` へ複製し、文言を本文に合わせて置き換える。

| 型 | 固定図 |
|---|---|
| Product North Star | `north-star-value-flow.svg`（対象・損なわれた価値・役割・望む状態の流れ）、`north-star-boundary.svg`（担う範囲と担わない範囲、判断原則） |
| Product Strategy | `strategy-choice.svg`（選ぶことと選ばないこと）、`strategy-action-chain.svg`（行動間の因果） |

### 経緯の扱い

経緯（出来事の時系列・試した案の履歴）を本文に残すかは型で決まる。型を決めた直後にこの値を `reader_context.history` へ写す。「前提へ畳む」場合は、結論へ影響する条件だけを主張の直前へ残す。

| 扱い | 型 | 理由 |
|---|---|---|
| 時系列で残す | 期間ダイジェスト | 「この期間に何が起きたか」が読み手の問いの答えそのもの。時系列は根拠である |
| 前提へ畳む | ADR、Product North Star、Product Strategy、RDB物理設計、トラブルシューティング、コンセプトドキュメント、実装解説（PR）、クラウドアーキテクチャ | 試した案は候補比較・発生条件・設計意図へ畳む。いつ試したか、誰がやったかは書かない。実装解説は変更前後の差分を残し、開発の試行は書かない |
| 書かない | README、ハウツーガイド、システム構成、業務知識・コアドメイン、ドメインモデル、ユーザー目的達成BDD、RDB論理設計、要求発見正本、利用・負荷モデル、品質要求正本 | 読み手は「今どうするか」「何であるか」を知りたい。業務と要求の型は、根拠状態を残し、作業の時系列は書かない |

`時系列で残す` の型でも、時系列を置くのは型の固定区画（期間ダイジェストの「動き」）だけである。

### 日付の書き方

| 型 | 書き方 |
|---|---|
| 業務知識・コアドメイン、ユーザー目的達成BDD、RDB論理設計、RDB物理設計のBDDと本文 | `YYYY年M月D日`。ハイフン区切りへ省略しない。時間帯は `YYYY年M月D日 HH:MMからHH:MMまで` |
| 期間ダイジェスト、ADR、システム構成、要求発見正本、利用・負荷モデル、品質要求正本、クラウドアーキテクチャのメタ情報と表 | `YYYY-MM-DD` |

業務を確定する型は、業務の場で読み上げられる形に合わせる。記録を追う型は、並べ替えと突き合わせができる形に合わせる。同じ文書の中で二つを混ぜない。

### 型の宣言

本文の冒頭かメタ情報に、型と読み手を明示する。読んだ人が「これは自分向けではない」と早く判断できることも成功条件である。

```
型: ハウツーガイド ／ 読み手: 定期実行ツールを導入済みで、ジョブを追加したい人
```

## この19型で扱わないもの

ユースケース、UX Journey map、検証記録、調査報告・スパイク結果、ロードマップを含むPRD、テスト計画・テスト観点、会議の議事録、ポストモーテム、決定ログ、論点台帳、ランディングページ、スタートガイド、チュートリアル、オンボーディング、APIリファレンス、用語集、Runbook、デザインドック／RFC、リリースノート、コードコメント、コード地図、コードリーディングは19型に無い。リポジトリ独自の型も足せない。依頼がこれらに当たる場合は、19型のどれで書くかを決められないことを依頼者へ伝え、近い型へ押し込まない。
