# インフラ構成の見本（抜粋）

この見本は、インフラ構成の資料で判断が分かれやすい箇所だけを、会議室の予約サービスの題材から抜き出したものである。題材の値や言い回しは写さず、どこで何を判断したかを見る。節の構成はテンプレートが持つ。

## 構成図を題名のすぐ下に置き、線の読み方を添える

読み手が最初に知りたいのは、何がどこで動き、どこが同期でどこが非同期かである。そこで構成図を最初に置き、線の読み方を一文で添えてから、構成を言い切った。図には要素の名前と主な流れだけを描き、選んだ理由は本文に書いた。

![構成図。予約者のブラウザから予約API、予約データベースへの同期の流れと、通知キューから通知ワーカー、メール配信への非同期の流れ](cloud-architecture.example.assets/infrastructure.drawio.svg)

> 実線は同期、点線は非同期を表す。AWS の東京リージョンの二つの AZ に、予約API と予約データベースを置く。通知は非同期にし、止まっても予約は続ける。

## 比べる領域は、要件と制約が答えを左右するものだけ

運用担当が2人という制約が、計算処理とデータベースの選択を左右したので、そこだけを候補と比べた。制約の効かない領域は、一覧を埋めるために比べない。運用の人数が多い題材なら、同じ領域でも制御面を自分で持つ案が残る。

> 計算処理には ECS on Fargate を選ぶ。EKS は制御面の運用が2人には重く、Lambda は予約API の常駐の接続と相性が悪い。代わりに、コンテナの更新と容量の検証は自分たちで持つ。

## 決まっていない条件に依存する選定は、言い切らずに見直す条件と組にする

リージョン全体の障害から何時間で戻すかが決まっていないので、単一リージョン・二つの AZ の構成を、決まった構成として言い切らなかった。復旧の目標が決まれば、同じ比較で、複数リージョンが要るかもここで決まる。

> 単一リージョンに置く。リージョン全体の障害で何時間止まってよいかはまだ決まっておらず、数時間以内と決まったら、複数リージョンへの複製を比べ直す。

## 障害時の振る舞いは、守る順位から決める

非機能要件の資料は、重複予約を残さないことを最優先にしている。だから、予約データベースが止まったら予約を受け付けず、通知が止まっても予約は続けると書いた。古い空き状況で予約を成立させるより、止めるほうを選ぶ。
