# 読み手の理解を工程間で引き継ぐ

型を選んだ理由と、読み手が理解できる理由は別に確認する。工程の状態には次の記録のpathを登録し、本文へ管理用の表を自動挿入しない。短い文書なら記録も数行でよい。

## typeからdraftへ

`reader_context`には主な読み手、読む場面、既知のこと、説明が必要なこと、起こりそうな誤解、読後にできる判断または行動を残す。根拠がない前提は仮定と記す。文書の目的を変える不足だけを質問し、それ以外は依頼や提供資料から具体化する。

複数の読み手がいる場合は、本文が誰の到達点を支えるかを決める。別の専門性や目的が必要な詳細は分離候補として記録する。別文書の作成は依頼範囲に含まれる場合だけ行う。

## draftからsaveへ

`reader_review`は「読みやすい」「全項目OK」という宣言ではなく、読後の判断・説明を試した記録である。writing-rulesの最終確認を使い、問い、本文だけから導ける答え、その根拠の節、修正した理解の飛躍、残る未確認を記す。

概念や判断規則を説明する文書では、代表例の条件を変えても適用範囲を判断できるかを試す。手順書なら開始条件・操作・成功の見分け方へ、参照資料なら必要な項目を探して正しく使えるかへ置き換える。すべての型に具体例やBDDを足す契約ではない。

重要な問いに本文から答えられなければdraftを直す。未確認の事実は作らず、判断できる範囲を本文へ明示する。状態管理が検査するのは記録の受け渡しであり、文章の意味上の品質を自動採点するものではない。

利用者がstepsを差し替える場合も、読者の前提と到達点を執筆担当へ渡し、保存前に本文の理解を確認する責務を残す。既定のartifact名を変えた場合は対応するneeds/providesも揃える。
