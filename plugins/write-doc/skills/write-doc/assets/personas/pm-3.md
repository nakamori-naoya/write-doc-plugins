# プロダクトマネージャー3年目

プロダクトの方向と優先順位を3年決めてきた。作る側の会話に入れるが、自分では実装しない。

## 実務で使える

**説明なしで使ってよい語である。**

- プロダクトの判断: 指標に基づく意思決定、仮説の立て方と検証、優先順位付け、やらないことを決めること
- 数字: リテンション、継続率、チャーン、コンバージョン、ファネル、コホート
- 進め方: 要件の整理、開発チームとの調整、リリースの計画、ステークホルダーとの合意形成
- デザイン: デザイナーとの協働、画面の意図を読むこと、ユーザー体験の議論（デザインは学習中）
- 開発の周辺: Git と GitHub の使用、プルリクエストを見ること、簡単なオリジナルアプリを作った経験

## 言われれば分かる

**初出で一言添えれば通じる。説明なしで論の土台には使えない。**

- API、データベース、非同期処理といった language の粒度の技術語
- 自分が関わった機能まわりの技術的な制約
- 環境が分かれていること、リリースに手順があること
- ログとエラーが記録されていること

**3年で覚えたのは、自分が関わった範囲の語だけである。** 関わっていない領域の技術語は、1年目と同じく分からない。

## 知らない

**目的と前提から説明しないと通じない。**

- プログラミング言語の文法、コードの読み方
- システムの内部構造、設計手法
- インフラ、クラウド、ネットワーク
- データベースの設計、トランザクション、性能
- 分散システムで起きること

## この人へ書くときに落ちやすいところ

- **技術的な制約を、判断の前提として説明せずに置く。** 「そこは技術的に難しい」だけでは、代案を出せない。何がどう難しいのかが要る。
- **指標を出さずに「良くなる」と書く。** この人は数字で判断する訓練を受けている。数字が無い主張は判断材料にならない。
- **実装の詳細を判断材料として渡す。** 判断に要らない詳細は、この人にとって全部枝葉である。
