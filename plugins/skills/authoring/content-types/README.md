# content-types

**何を書くかを決める。** 読み手と目的から文書の型を1つ選び、その骨格を渡す。

**規律も媒体も知らない。** どう書くか・どう出すかは、それぞれ別の関心である。

## 使う

```
/pick-content-type      型を決めて、骨格を取る
```

## 28種のカタログ

「選び方」を上から順に判定する。**決まった型の詳細だけ**を読む（全部読まない）。

| 群 | 型 |
|---|---|
| プロダクトの方向と経路を決める | Product North Star / Product Strategy |
| 業務を確定する | 業務知識・コアドメイン |
| 目的達成を端から端まで共有する | E2E BDDシナリオ |
| データを永続化する | RDB論理設計 / RDB物理設計 |
| 追う | 期間ダイジェスト / 決定ログ / 論点台帳 |
| 学ぶ | スタートガイド / チュートリアル / ハウツー / コンセプト / オンボーディング |
| 引く | API リファレンス / 用語集 / トラブルシューティング / Runbook |
| 決める | ADR / デザインドック / ポストモーテム / リリースノート |
| コードと入口 | コードコメント / README / ランディングページ / 実装解説（PR） |
| コードを説明する | コード地図（マクロ） / コードリーディング |

**コードを説明する型は3つあり、読み手の問いで分かれる。** どこに何があるか（コード地図）／この処理はどう動くか（コードリーディング）／この変更で何が変わったか（実装解説（PR））。**混ぜない。**

各型に**読み手・読み手の状態・目的**が付く。専門領域の内容の正しさや作業方法は呼び出し元が与え、content-typesは補わない。

各テンプレートの節にはHTMLコメントで**「書く内容」と「書かない内容」**を持たせる。見出しだけを渡して内容を推測させない。コメントは執筆時の境界であり、本文を満たしたら成果物から削除する。リポジトリのlintが、全節に両方の境界があることを検査する。

## 設定

```yaml
# <repo>/.harness-plugins/content-types.config.yml
version: 1
default_type: concept           # 型が特定できないときの既定
instructions:
  selection:
    directive: catalogの選び方を上から判定し、型を1つだけ選ぶ
```

このファイルだけで完結させる。personal設定や同梱既定から不足キーは補われない。

テンプレートはプラグイン同梱の28種だけを使う。テンプレートと記載例の対応は`assets/template-examples.yml`を正本とし、選んだ型に対応する両方を読む。記載例はテンプレートを埋める前に全文を読む。リポジトリ独自テンプレート、独自の型、同名テンプレートの上書きは受け付けない。旧`templates_dir`が残っていればresolverが停止する。

**`default_type` に対応するテンプレートが無ければ止まる。** 存在しない骨格を探しにいかせない。

## しないこと

- 文章を書かない
- 媒体の書式を決めない
- **テンプレートの見出し構成を勝手に変えさせない。** 埋められない節は削らず「なし」と書く（空欄と「なし」は別の情報である）
