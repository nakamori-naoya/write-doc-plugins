# データモデリングの型

## RDB論理設計

**読み手**: 業務を知る人と、業務事実をRDBへ永続化する人

**目的**: 永続化の作成・更新・削除に関係する業務シナリオから、時間を越えて残す事実とRDBの論理テーブル構造を決める

**成功条件**: BDDシナリオ、記録する事実、論理テーブル・列・業務制約が双方向に対応し、物理設計の関心が混ざっていない

**境界**: RDBを前提に、業務イベントと事前状態から「何を論理テーブルへ残すか」を決める型である。論理テーブル、論理列、候補キー、参照関係、業務制約、正規化を扱う。DBMS製品と版、物理型、索引、分離レベル、DDLは扱わない。API、DTO、ORM、画面も永続化する業務事実ではないため扱わない。Readの検索形と性能はRDB物理設計で扱う。

作成・更新・削除に関係する業務シナリオをBDDにし、資料の最後にまとめる。正常な成立だけでなく、拒否、取消、訂正、削除、同時進行で守る結果まで扱う。各BDDは前のBDDへ依存させず、GivenとAndに必要な事前状態をすべて書く。BeforeとAfterには全論理テーブルを同じ順序で、全カラムの見出しを持つMarkdown表として記載する。0件でも表を省略せず、見出し行と区切り行に続けて、全セルへ`&nbsp;`を1つずつ置いた表示上空白のデータ行を1行だけ置く。完全な空セルはレンダラーによって行高が潰れるため使わない。各表の直後には`<br>`を置いて表示上も1行空ける。変化しない表もBeforeの全行をAfterへ再掲する。論理データモデル図はMermaidの`erDiagram`で全テーブル、列、キー、多重度を示す。モデルからBDDを説明でき、BDDから記録の置き場を辿れることが完了条件である。

## RDB物理設計

**読み手**: DB設計者、実装者、運用者

**目的**: 検査済みの論理データモデルを変えず、指定したRDB製品と版で実現・運用する方法を決める

**成功条件**: 論理テーブル・列・業務制約が不変で、物理名、型、制約、索引、分離レベル、配置、容量・性能・運用に対象版の根拠がある

**境界**: RDB論理設計で決めた「何を残すか」を、対象DBMSと正確な版で「どう実現するか」へ写す型である。論理設計のER図、CUDのBDD、Before / Afterは再掲しない。Readについては検索条件、結合、並び順、件数、鮮度、一貫性、SLOを代表的な読み取りとして記載する。物理設計で論理構造の変更が必要になったら、この資料で補わずRDB論理設計へ戻す。

索引と分離レベルは物理設計に属する。分離レベルは名称だけを選ばず、論理設計が要求する同時実行上の保証、対象版で防げる現象、制約・ロックとの併用を判断する。さらにtransaction境界、SQL順序、競合検知、rollback、業務結果への変換、再試行上限まで具体化する。
