# コードに注釈を振る

**コードを載せた文書の本体は、コードそのものではなく、コードに振った注釈である。**

コードだけ貼っても、読み手は「どこを見ればいいか」が分からない。逆に文章だけで説明すると、読み手は自分でコードを開いて対応を取る羽目になる。**注釈は、その2つを1つの画面で対応させるための仕組みである。**

## 注釈には用途が2つある

**何を分からせたいかで、規律が変わる。** どちらの用途かを決めずに書くと、注釈の粒度が途中で入れ替わり、読み手が現在地を失う。

| 用途 | 読み手の問い | 並べる軸 | 注釈が答えるもの |
|---|---|---|---|
| **差分注釈** | この変更で何が変わったのか | 変更の単位 | その行が新規か、変わっていないか、なぜそうしたか |
| **実行順注釈** | この処理はどう動くのか | 呼ばれる順 | その行で何が確定し、どこへ分岐し、何が外へ出るか |

**1つの文書で混ぜない。** 差分注釈の途中に「ここで9件が確定する」が混ざると、読み手はそれが変更点なのか元からの挙動なのか判別できなくなる。

## 共通の規律

**① 掲載は2層に分ける。**

| 層 | 何を載せるか | 注釈 | 畳んでよいか |
|---|---|---|---|
| **読ませる層** | 読み手に実際に読ませたいコード | **必ず振る** | **畳まない** |
| **参照させる層** | 疑わずに済ませるための残り | 任意 | 畳んでよい |

**読ませる層を畳んだ時点で、その文書は読まれない。** 開かなければ1行も現れないコードは、載せていないのと同じである。

**参照させる層に何を置くかは、文書の型が決める。** 規律の側は「2層に分ける」という形式だけを言う。

**② 省いたことを、省いた場所で示す。**

読ませる層は選んで載せる。**選んだ以上、省いた箇所に印を置き、原典（行番号つきの恒久リンク）へ到達できるようにする。** 印が無いと、読み手は載っているものが全部だと読む。

**生成物・巨大な JSON・mock を読ませる層へ置かない。** 注釈を振れないものを並べると、資料全体の注釈密度が薄まり、読み手は「注釈を探す」読み方をやめる。

**③ 注釈をコードの前だけに置かない。途中へ差し込む。**

前置きだけで長いコードを渡すと、読み手は途中で現在地を見失う。**説明したい行の直前へ挟む。** コードの後ろにまとめて書くのも同じ理由で駄目で、行番号を目で往復させることになる。

**目安は、掲載20行につき1つ以上。** ただし**これは自己点検の目安であって合否ではない。** 20行が1つの意味単位である関数と、200行が1つの意味単位である表駆動テストに、同じ密度を要求するのは誤りになる。

## 差分注釈の規律

**変わっていない行にも注釈を振る。**

これが一番効く。注釈が新規の行にしか付いていないと、**読み手は画面にある全部が新規だと読む**。「この行は旧実装と一字一句同じ」と書いてあることに価値がある。

**要求するのは読ませる層に載せた行についてだけである。** 参照させる層の全行に区分を振る義務は無い（守れない規律は、安いほうだけが守られて終わる）。

凡例を**文書の冒頭に必ず置く。** 置かないとこの規律が機能しない。

| 表記 | 意味 |
|---|---|
| ［新規］ | 旧実装に無かった行 |
| ［ロジック変更なし］ | 呼ぶメソッド・条件・引数とも旧実装と同一 |
| ［コメントのみ変更］ | コードは同一で、コメントの文言・配置だけが変わった |
| ［削除］ | 旧実装にあって、今は無い |

**「何行目が」「どの区分で」「なぜそうなのか」の3つ**を書く。

```
17〜21行目・import 変更 — 旧実装が使っていた utility（1/10 の抽選用）を削除し、
新ロジックの閾値判定に使う vote_lower_limit_service を追加。旧ロジックが
丸ごと消えたことに伴う入れ替え。
```

## 実行順注釈の規律

**注釈は、その行を通過したときに何が起きたかを書く。** 区分ではなく、状態の変化である。

凡例を冒頭に置く。**差分の凡例とは別物で、同じ文書に両方を置かない。**

| 表記 | 何に付けるか |
|---|---|
| ［入力］ | この段階が受け取った値と、その出どころ |
| ［確定］ | この行を抜けた時点で決まった値 |
| ［分岐］ | 条件と、どちらへ行くか。**両方の行き先を書く** |
| ［副作用］ | DB・キャッシュ・ログなど、外へ出るもの |
| ［次へ］ | 次にどこを呼ぶか |

**分岐と副作用の行には必ず注釈を振る。** ここを飛ばすと、読み手は「なぜここで終わったのか」を後から逆算する羽目になる。

**同じことを2度書かない。** 直前の段階で説明した値に、次の段階でもう一度「これは何か」を書くと、読み進める速度が落ちる。**2度目は参照だけにする**（「段階3で確定した cacheKey」）。

**呼び先へ潜るかどうかを、その場で宣言する。** 潜らないなら「ここでは追わない」と書く。書かないと、読み手は続きがあると思って探す。

### 実行順注釈は、幹を完走してから枝へ降りる

**幹は対象処理の主要な制御フローである。** 幹の途中へ呼び先の詳細コードを挟まない。呼び先の中身を見なくても入出力を説明できるなら、その場には呼び出し行と戻り値の意味だけを置き、詳細は文書下部の枝へ送る。

- 幹から枝へは、呼び出し行の注釈にページ内リンクを置く
- 枝の冒頭から、呼び出し元の幹へ戻るリンクを置く
- 枝は幹で初めて呼ばれた順に並べる
- 分岐から複数の実装へ進む場合、実装本体は原則として枝へ置く
- 枝からさらに呼ぶ先は原典リンクで打ち切り、多段の枝を作らない

**別ファイルだから機械的に枝へ送るわけではない。** 数行のコードが幹の主張を直接証明し、その場で読む方が往復より速いなら、残す理由を注釈して幹へ置いてよい。

## 書かないこと（両方に共通）

- **コードを日本語に翻訳しただけの注釈。** 「err が nil でなければ return する」は、コードを読めば分かる。**書くのは、その行が処理全体の中で持つ意味である**
- **推測した意図。** 原典（コード上のコメント・PR・コミット）に無い理由を書かない。無ければ**「言及なし」**と書く
- **レビュー意見。** 直すべき点は別の節・別の文書へ分ける。注釈に混ぜると、事実と意見の区別が消える

## 出す前に

**共通**

- [ ] 用途（差分／実行順）をどちらか一方に決めた
- [ ] 凡例を冒頭に置いた（用途に合う側のものだけ）
- [ ] **読ませる層のコードが、既定で見えている**
- [ ] 注釈が**コードの途中にも**入っている（前置きだけになっていない）
- [ ] 省略した箇所に印があり、原典へ到達できる
- [ ] コードを翻訳しただけの注釈が無い
- [ ] 推測した理由を書いていない（無ければ「言及なし」）
- [ ] レビュー意見を注釈に混ぜていない
- [ ] ファイルパスが開けるリンクになっている
- [ ] 秘匿（トークン・鍵・実データ）がコードに含まれていない

**差分注釈のとき**

- [ ] **変わっていない行にも注釈が付いている**（読ませる層の各ブロックに最低1つ）

**実行順注釈のとき**

- [ ] **分岐と副作用の行すべてに注釈が付いている**
- [ ] 各段階に「入力・確定する値・分岐条件・副作用・次の呼び出し」が揃っている
- [ ] 潜らない呼び先に「ここでは追わない」と書いた
- [ ] 幹だけを上から読んで、入口から出口までの主要な流れが通る
- [ ] 呼び先の詳細を枝へ分け、幹と枝に往復リンクを置いた
- [ ] 枝の中へさらに枝を作っていない
