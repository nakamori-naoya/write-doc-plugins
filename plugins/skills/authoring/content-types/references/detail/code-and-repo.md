# コード・リポジトリまわりの型

## コードコメント

**読み手**: そのコードを読む人（数か月後の自分を含む）
**目的**: コードそのものからは読み取れない**意図と文脈**を残す
**成功条件**: 読み手が「なぜこうなっているか」を推測せずに済む

「コードを明確にすればコメントは不要」という主張はある程度正しいが、**コードは「何をしているか」しか語らない。** なぜその選択をしたか、なぜ素直な実装を避けたかは、コードに書けない。

書くこと。

- なぜこの実装にしたか（採らなかった選択肢がある場合は特に）
- 前提と制約（外部仕様、既知のバグの回避、性能上の理由）
- 危険な副作用、触ると壊れるもの

書かないこと。

- コードを読めば分かること（`i を 1 増やす`）
- 嘘になりうる説明（コード変更時に更新されない記述）

**テンプレート**: [`assets/templates/code-comment.md`](../../assets/templates/code-comment.md)

## README

**読み手**: リポジトリに来た人
**目的**: **これが何か**と**最初の一歩**を渡す
**成功条件**: 読み手が「自分に関係あるか」を判断でき、関係あるなら次の一歩へ進める

README はリポジトリのチートシートであり、その先のドキュメント群の土台になる。**簡潔・有益・正確・最新**であること。コードを変えたら README も追随させる。

重要なサブフォルダにも README を置いてよい。

**テンプレート**: [`assets/templates/readme.md`](../../assets/templates/readme.md)

## ランディングページ

**読み手**: 何かを探しに来た人
**目的**: **読む量を最小に**して、適切な行き先へ振り分ける
**成功条件**: 読み手が短時間で正しいページへ到達する

道路の大きな標識に相当する。短く、目を通しやすく、専門用語を使わない。**ユーザーにとって最も重要で関連のある情報だけを強調し、後から必要になる複雑さは隠す。**

情報の並べ方は3通り。組み合わせてよい。

| 構造 | 形 | 向くもの |
|---|---|---|
| シーケンス | 順番に並ぶ | 手順、索引、用語集 |
| 階層 | 親子で降りていく | 全体像から詳細へ |
| Web | 相互リンク | 読み手が順番を決める |

**テンプレート**: [`assets/templates/landing-page.md`](../../assets/templates/landing-page.md)
**トップレベルの分類は、ユーザー調査と組織の戦略目標から決める。** 自分たちの組織図をそのまま出さない。

## 実装解説（PR）

**読み手**: レビュアー、後任、その実装を引き継ぐ人
**目的**: **1つの変更（PR）が何をしたか**を、全体の骨格とコード注釈の両方で分からせる
**成功条件**: **この1本を読めば、PR の差分を自分で追わなくてもレビューできる**

コードレビューのコメントとも、ADR とも違う。**ADR は「なぜそう決めたか」、実装解説は「実際にどう入っているか」。** 決定の記録ではなく、**入ったコードの案内図**である。

構成は「上から下へ、抽象から具体へ」で固定する。

1. **処理の流れ** — 番号つきの手順。ここだけで筋が追える
2. **何が変わったか** — 変更の単位ごとに、区分（新規／置き換え／シグネチャ変更／廃止）と理由
3. **実装の全文** — **省略しないコード＋注釈**
4. **テスト設計** — 何を確かめているか
5. **気になった点** — レビューで見るべき点。重大度つき

**3が本体である。** 抜粋を貼るだけの解説なら PR の diff を見れば足りる。**全文に注釈を振ることに価値がある。**

注釈の付け方には規律が要る。**変わっていない行にも注釈を振る**のが要点で、これを守らないと読み手は画面にある全部が新規だと読む。注釈の規律そのものは、文章の規律の側が持つ。

**推測した理由を書かない。** PR 本文にもコミットにも無い意図を補うと、それが事実として読まれる。述べられていなければ「言及なし」と書く。

**レビュー意見をコード注釈に混ぜない。** 5 の節へ分ける。混ぜると事実と意見の区別が消え、注釈全体が信用されなくなる。

**この型は差分を説明する型であって、処理を追わせる型ではない。** 読み手が「変更点」ではなく「この機能はどう動くのか」を知りたいなら、それはコードリーディングの仕事である。

**テンプレート**: [`assets/templates/pr-walkthrough.md`](../../assets/templates/pr-walkthrough.md)

## コード地図（マクロ）

**読み手**: そのコードベースへ入る人、久しぶりに戻る人、他チームからレビューに呼ばれた人
**目的**: **どこに何があり、どの層がどう積まれているか**を1枚で渡す
**成功条件**: 読み手が、次に読むべきディレクトリとファイルを**自分で選べる**

**空間の文書である。** 実行の時間軸ではなく、置き場と境界で並べる。**ディレクトリ構成・層の分かれ方・重要な入口・アーキテクチャ上の特徴**がここに入る。

構成は次で固定する。

1. **何をするシステムか** — 1〜3文。ここで読み手が自分に関係あるか判断する
2. **地図** — ディレクトリ構成と、各ディレクトリの責務
3. **層と依存の向き** — 誰が誰を呼ぶか。**逆流していないこと自体が仕様である**
4. **重要な入口** — ここから読み始めれば良い、という数点
5. **アーキテクチャ上の特徴** — 素直な実装を避けている箇所と、その理由
6. **次に読むもの** — 個別処理を追いたい人をコードリーディングへ渡す

**コードを大量に貼らない。** 貼るとしても、境界を示す型定義やインターフェースの数行に留める。**行を追わせたくなった時点で、それはコードリーディングの仕事である。**

**網羅しない。** 全ディレクトリを列挙した地図は目次であって地図ではない。**読み手が最初に触る場所から埋める。**

**テンプレート**: [`assets/templates/code-map.md`](../../assets/templates/code-map.md)

## コードリーディング

**読み手**: その処理を**自分で追おうとしている**開発者（レビュー前の予習、障害調査、引き継ぎ）
**目的**: **1つの処理を、入口から出口まで実行順に追わせる**
**成功条件**: **上から読み下すだけで、どの値がどこで確定し、どこで分岐し、何が外へ出たかを言える**

**時間の文書である。** ファイル順でもディレクトリ順でもなく、**呼ばれる順**に並べる。1つの段階が複数ファイルにまたがることも、1つのファイルが複数の段階に現れることもある。**それでよい。**

構成は次で固定する。

1. **何を追うか** — 対象の処理、入口、出口、追わない範囲
2. **幹の一覧** — 番号つき。ここだけで主要な制御フローが追える
3. **幹を実行順に読む** — 段階1つにつき1ブロック。**主要ロジックのコードと、コード途中に差し込んだ注釈**
4. **枝を読む** — 幹から呼ぶ別パッケージ・補助ロジックの詳細。幹との往復リンクを持つ
5. **分岐と終端の一覧** — どの条件でどこへ抜けるか
6. **未確認・追っていないもの** — 読んでいない先、確かめていない前提
7. **付録** — 型定義・インターフェースなど、実行順を持たない参照情報

**3の幹が本体である。** 読み手は枝を開かなくても、入口から出口までの主要な流れを言えなければならない。各段階には必ず次の5つを書く。

| 項目 | 何を書くか |
|---|---|
| 入力 | この段階が受け取る値と、その出どころ |
| 確定する値 | この段階を抜けた時点で決まっているもの |
| 分岐条件 | どの条件でどちらへ行くか |
| 副作用 | 外部（DB・キャッシュ・ログ）へ出るもの |
| 次の呼び出し | 次にどこへ渡すか |

**コードは本体であり、既定で見えていること。** 畳んだコードは読まれない。**上から読むと1行もコードが現れない資料は、この型として失敗している。**

**掲載は選ぶ。全文ではない。** 実行順に追うのに要る部分を選び、**省いた箇所は省いたと印を置き、原典（行番号つきの恒久リンク）へ到達できるようにする**。生成物・巨大な JSON・mock を本体へ置かない。

**幹と枝を混ぜない。** 幹には、対象処理の順序・主要な分岐・終端を所有するコードを置く。呼び先の実装を見なくても入出力を説明できるなら、幹には**呼び出し行・戻り値の意味・枝へのリンク**だけを残し、実装は下部の「枝」へ置く。

次の順で判定する。

1. `if` / `switch` から複数の実装へ分かれる呼び先は、実装本体を原則として枝へ置く。幹には分岐条件と行き先を残す
2. 呼び先の実装を外しても「入力・確定する値・分岐・副作用・次」を説明できるなら枝へ置く
3. 別パッケージ・別層へ越える呼び先は枝候補。ただし、数行のコードが幹の主張を直接証明するなら、理由を注釈して幹へ残してよい
4. 枝から呼ぶ先は原則として原典リンクで打ち切る。枝の中へさらに枝を作らない

**枝は付録ではない。** 枝は「確認する価値がある実行ロジックだが、先に読むと幹を見失うもの」。付録は型定義・インターフェースなど、実行順を持たない参照情報である。

枝は**幹で初めて呼ばれた順**に並べる。幹の呼び出し注釈から `#branch-<関数名のケバブケース>` へリンクし、枝の冒頭から呼び出し元の `#stage-N` へ戻せるようにする。同じ枝を複数箇所から呼ぶ場合も枝は重複させない。

**注釈をコードの前だけに置かない。** 前置きだけでは、読み手は長いコードの途中で現在地を見失う。**分岐・確定・副作用の各行の直前へ差し込む。**

**「なぜそう書いたか」は書けるなら書き、書けないなら書かない。** 実装意図が原典に無ければ**「言及なし」**と書く。**推測を事実として書かない。**

**レビュー意見を混ぜない。** 直すべき点が見つかったら、それは実装解説（PR）かレビューコメントの仕事である。

## コード説明の3つの型をどう選ぶか

**同じコードを説明する型が3つあるのは、読み手の問いが3つ違うからである。**

| 型 | 読み手の問い | 並べる軸 | 単位 | コードの扱い |
|---|---|---|---|---|
| **コード地図（マクロ）** | どこに何があるのか | 空間（置き場・層） | ディレクトリ・層 | ほとんど貼らない |
| **コードリーディング** | この処理はどう動くのか | 時間（実行順） | 段階（呼び出し） | **選んで貼り、途中に注釈** |
| **実装解説（PR）** | この変更で何が変わったのか | 差分 | 変更の単位 | 変更ファイルを全文＋注釈 |

**判定は「読み手がすでに何を知っているか」で決める。**

- どこを開けばいいか分からない → **コード地図**
- 開く場所は分かるが、追うと迷子になる → **コードリーディング**
- 動くことは知っていて、今回の変更の可否を判断したい → **実装解説（PR）**

**混ぜない。** 地図に行番号つきのコードが並び始めたら、それはコードリーディングを地図に埋め込んでいる。実装解説を実行順に並べ替え始めたら、それは2つの型を1本でやろうとしている。**分けて相互リンクする。**

**1つの PR に対して、実装解説とコードリーディングの両方を書いてよい。** 型が2本になるのであって、1本に2つの型が入るわけではない。
