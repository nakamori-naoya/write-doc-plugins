# システム構成の見本（抜粋）

この見本は、システム構成の資料で判断が分かれやすい箇所だけを、会議室の予約サービスの題材から抜き出したものである。題材の値や言い回しは写さず、どこで何を判断したかを見る。節の構成はテンプレートが持つ。

## 要素を分けた理由は、今の構成の狙いとして本文に書く

APIとワーカーを別のサービスにした理由は、今の構成が守っている狙いなので本文に一文で書いた。なぜ別の方式を見送ったかという比較は、この資料ではなく決定の記録に任せる。狙いの無い分け方なら、理由を作らずに構成だけを書く。

> 利用者のWebリクエストを処理する `roomflow-api` と、期限切れのタスクを処理する `roomflow-worker` は、別々のコンテナとして Cloud Run 上で動く。Webからのリクエストが急に増えたときにも、期限切れ処理の負荷で同期APIの応答が遅れないようにするためである。

## 通信ごとに、相手が応答しないときの振る舞いを書く

図の矢印だけでは、障害時に何が残るかが読めない。そこで通信ごとに経路、認証、相手が応答しないときの結果を並べ、行をまたいで比べられるようにした。

| 呼ぶ側 → 呼ばれる側 | 経路 | 認証 | 相手が応答しないとき |
|---|---|---|---|
| roomflow-api → roomflow-hold-expiry | タスク登録（非同期） | サービスアカウント `roomflow-api@` | 登録に失敗したら仮押さえ自体を失敗させる。期限の無い仮押さえを作らない |
| roomflow-hold-expiry → roomflow-worker | HTTP push、期限時刻に配送 | OIDCトークン（`roomflow-tasks@`） | 最大5回再試行する。5回失敗したタスクはキューに残り、日次の点検で拾う |

## 実測と推定を分け、推定の出し方を書く

同時受付は実測の最大値と推定の上限が混ざりやすいので、値ごとに「実測」「推定」を付け、推定の式を添えた。コンソールや設定で照合できる値なら、推定と書かずに照合した時点を書く。

> 同時受付の実測値は、2026年8月の1か月についてCloud Loggingを1分単位で集計した最大値である。推定上限は、1インスタンスあたり15〜20件/分の実測と最大10インスタンスから算出した。

## 決まっていない構成は、未決に影響先と決め手を置く

> リージョン障害時の目標復旧時間。影響する要素: すべて。運用責任者が判断する。決まるまでは「停止する」のままとする。
