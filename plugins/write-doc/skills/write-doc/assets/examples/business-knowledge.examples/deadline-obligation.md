# 業務知識の見本（抜粋）：期限つきの義務が続く業務

この見本は、期限つきの義務が続く業務で一つの事実の置き場に迷いやすい箇所だけを、購買申請の承認を題材に抜き出したものである。題材の値や言い回しは写さず、どこで何を判断したかを見る。節の構成はテンプレートが持つ。

## 期限は計算に置き、状況は期限を名前で持つだけにした

「課長は5営業日以内に承認する」という一文には、期限の求め方と、期限を持って待っている在り方が混ざっている。求め方は計算に置き、どの時点の営業日カレンダーを使うかもそこに書いた。状況は、承認期限を持つことを名前で言うだけで、日数を書き直さない。

```markdown
## 前提

### 営業日カレンダー

どの日が営業日かは、総務の業務が決める。この業務は、日ごとの指定を読むだけである。

## 状況

### 課長の承認待ち（AwaitingManagerApproval）

課長がまだ承認も差し戻しもしていない購買申請。承認期限を持つ。

### 部長の承認待ち（AwaitingDirectorApproval）

部長がまだ承認も差し戻しもしていない購買申請。承認期限を持つ。

## 計算

### 承認期限

その承認待ちになった日以後の営業日を早い順に数えて、5日目の日とする。営業日カレンダーは、その承認待ちになった時点のものを使う。その後に営業日カレンダーが変わっても、承認期限は変えない。
```

## 時刻が来ることを、アプリが起こすきっかけとして表に置いた

期限を過ぎたときに何が起きるかは、人の行動と同じ表に、時刻の到来をきっかけにした行として置いた。きっかけは「承認期限を過ぎる」ではなく「承認期限の翌日になる」と書き、期限の日のうちに承認できるかという境界を一つに決めた。期限を持たない状況にも同じきっかけの行を置いた。表に無い組み合わせを残さないためで、根拠は、そのきっかけを受けない状況の名前で足りる。

```markdown
## 行動・出来事と判断


| いつ | 誰が | 何をすると | 何が起きる | どの決まりによるか |
|---|---|---|---|---|
| 課長の承認待ち | アプリ | 承認期限の翌日になる | 部長の承認待ちになり、「承認者を繰り上げた（ApproverEscalated）」が起きる | 承認期限 |
| 部長の承認待ち | アプリ | 承認期限の翌日になる | 差し戻し済みになり、「期限切れで差し戻した（ReturnedByExpiry）」が起きる | 承認期限 |
| 承認済み、差し戻し済み | アプリ | 承認期限の翌日になる | できない。何も変わらない | 承認済み、差し戻し済み |
```

## 「いつまでに必ず決着するか」は、制約に義務として書いた

表は、来たきっかけへの答えしか持たない。誰も動かないまま時間が過ぎることは、表のどの行にも当たらないので、「必ず決着する」という約束は表では書けない。そこで、約束を制約に、いつでも成り立つ形（〜のままの申請は無い）で書き、表では表せないことを明示した。「期限を過ぎると差し戻す」と書くと、きっかけと結果の文になり、表の行の写しになる。

義務を実際に果たすのは、上の表の時刻が来る行である。人が動かなくても最後はアプリの行で決着するように行を並べた。行をつないだ結果が義務に収まるかは表の形からは読めないので、最も遅い経路を BDD に一件置いた。

````markdown
## 制約

### 決着の期日

申請した日以後の営業日を早い順に数えて10日目の日を過ぎて、課長の承認待ちか部長の承認待ちのままの購買申請は無い。破れると、申請した人は発注してよいか分からないまま、納期を逃す。この義務は、行動・出来事と判断の表では表せない。表は来たきっかけへの答えを持ち、きっかけが来ないまま時間が過ぎることを扱えないからである。

## BDD

### [BDD-007] 誰も承認しなくても、申請は10営業日目の翌日に差し戻し済みになる

```gherkin
Given: 購買申請 P-0001 は2026年6月1日（月）に申請され、課長の承認待ちである
  And: 2026年6月の営業日は、土曜日と日曜日を除くすべての日である
  And: 課長も部長も、承認も差し戻しもしない
When: 2026年6月6日になり、続いて2026年6月13日になる
Then: 2026年6月6日に部長の承認待ちになり、承認期限は2026年6月12日になる
  And: 2026年6月13日に差し戻し済みになる
```
````
