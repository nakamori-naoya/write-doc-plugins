# 構成ガイド（既定）

**文書全体の骨格**——何をどの順で並べるか——の規約。各セクションの中をどう書くかは `section` ガイドが持つ。

差し替えたい場合は`.harness-plugins/writing-rules.config.yml` の `rules.structure` に自分のファイルを指す。

## 既定: 全体像から詳細へ

読み手が最初に受け取るのは地図であって、道順ではない。

```
1. 一言でいうと        ← 1〜2文。ここだけ読んで立ち去れる
2. 全体像              ← 構成要素と関係。図を置くならここ
3. 各要素の概要        ← 表。1要素1行
4. 各要素の詳細        ← 節に分ける
5. 例外・限界・未確認  ← 隠さない
```

- **各段で完結させる。** 途中で読むのをやめた人が、そこまでで筋の通った理解を持って帰れる。
- **前の段で使っていない語を、後の段の見出しに出さない。** 用語は出す前に定義する。
- **同じ深さの節は同じ粒度で書く。** 片方だけ詳しいと重要度を誤解される。

## 冒頭要約と末尾総括

長い文書（画面3つ分以上）には両方を置く。**同じことを2回書かない。**

| | 役割 |
|---|---|
| 冒頭要約 | 読み**始める前**に頭へ入れる要点。「一言でいうと」＋箇条書き |
| 末尾総括 | **構造で**振り返る。何を問い、どう答えたか。要点の再掲ではない |

末尾総括が冒頭要約のコピーになっていたら、どちらかを消す。

**要約は役ごとに割る。** 要約が答える問いは複数ある（何が課題か、何を推すか、何を判断してほしいか、何が未決か）。**問いの数だけ段落か箇条書き項目を作り、各項目の1文目にその問いの答えを置く。** 1つの塊へ続けて書くと、読み手が自分で役を切り直すことになる。

**要約は最も読まれる場所なので、最も細かく割る。** 本文なら許される長さの段落も、要約では割る。

## 選べる構成型

依頼や型に応じて選ぶ。

| 型 | 形 | 向くもの |
|---|---|---|
| 段階的開示 | 全体像 → 詳細 | 既定。設計・仕様・概念 |
| 時系列 | 起きた順 | 障害報告・議事録サマリ・経緯 |
| 問題→解決 | 現状 → 課題 → 打ち手 → 帰結 | 提案・設計判断 |
| 手順 | 番号付きの一本道 | 手順書・スタートガイド |
| 症状引き | 症状 → 切り分け → 対処 | トラブルシューティング |
| 比較 | 軸を決めて表 → 判断 | 技術選定 |
