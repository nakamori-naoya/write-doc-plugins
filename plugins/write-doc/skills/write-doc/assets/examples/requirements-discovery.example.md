# 要件の見本（抜粋）

この見本は、要件の資料で判断が分かれやすい箇所だけを、会議室の予約サービスの題材から抜き出したものである。題材の値や言い回しは写さず、どこで何を判断したかを見る。節の構成はテンプレートが持つ。

## 具体的でも、決めた人がいなければ要件として言い切らない

「通知は60秒以内なら待てる」は数字まで具体的だが、5人への聞き取りから置いた見立てで、決める人の合意が無い。だから要件として言い切らず、見立てであることを文の言い方で示し、「まだ決まっていないこと」へ決め方と組で置いた。決める人が対象と期限を指定して合意していれば、同じ文でも要件になる。変わるのは合意の有無で、文の具体性ではない。速さの目標そのものは非機能要件の資料が持つので、ここでは値を写さない。

> 通知を何秒以内に届けるかは、まだ決まっていない。5人への聞き取りでは「60秒以内なら待てる」という見立てが出ており、非機能要件の資料ではこれを仮置きの目標にしている。対象者と場面を増やして確かめ、運用責任者が決める。

## 入力に無くても、特性から避けるべき失敗が導けるなら要件にする

入力に「同時予約を防げ」とは書かれていなかったが、人気の枠へ要求が集中するという特性と、電話台帳で起きていた重複から、避けるべき失敗が導ける。そこで因果を本文に書き、方式（ロックや制約の種類）は書かなかった。集中の度合いの値は非機能要件の資料が持つので、ここではリンクするだけにする。

> 人気の利用枠は公開直後に予約が集中する。電話台帳では同じ時間帯への重複予約が月12件起きていた。そのため、同じ利用枠への同時の予約で、成立する予約は一件だけにする。空き状況の表示が古くても、予約を成立させる時点で重複を防ぐ。

## 手段は、固定された制約と、後で選ぶものに分ける

「既存のID基盤で認証する」は、事業責任者が範囲と時点を決めた必須の条件なので「前提にする制約」に置いた。通知の経路（メールかプッシュか）は、利用者の選択で方式が変わるので要件に入れず、「まだ決まっていないこと」へ送った。同じ製品名でも、提案なら後で選ぶもの、決める人が指定した必須なら制約になる。

> 利用者の認証は、組織の既存のID基盤に任せる。事業責任者が、初回の公開の範囲で決めた条件である。
