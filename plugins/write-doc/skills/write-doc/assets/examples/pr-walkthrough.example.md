# PRの案内の見本（抜粋）

この見本は、PRの案内の資料で判断が分かれやすい箇所だけを、会議室予約の仮押さえの題材から抜き出したものである。題材の値や言い回しは写さず、どこで何を判断したかを見る。節の構成はテンプレートが持つ。

## 冒頭は、何を変え、何を変えていないかを言い切る

この題材では、既存のDB制約と取消の処理がすでにあり、変えたのは一つの関数のエラー変換だけだった。レビュアーが差分の大きさを読み違えないよう、変えていないことも冒頭で言う。変更が広い題材なら、変えた範囲の境目を先に書くことになる。

> 既存のDB制約が仮押さえの重複を拒否したとき、予約作成の呼び出し元へ`SLOT_UNAVAILABLE`を返すようにした。DB制約と、失敗時に予約と占有の両方を取り消す処理は、すでにある。今回変えたのは、一つの関数のエラー変換だけである。

## 注釈は、変えた行と、読まないと差分の意味が分からない行にだけ置く

`await`を足した一行は、見た目は小さいが、非同期の失敗を`catch`へ渡すための変更なので注釈で理由を書いた。変えていない行のうち、公開する関数の形を保ったことは呼び出し元に効くので注釈を置き、それ以外の変わらない行には置かない。

```typescript
▼［ロジック変更なし］公開する関数名・引数・戻り型を維持したため、呼び出し元は変えなくてよい
export async function createTentativeHold(input: HoldInput, repository: Repository) {
  try {
    ▼［新規］旧実装の return repository.createTentativeHold(input); を置き換えた。await を足して非同期の失敗を catch へ渡す
    return await repository.createTentativeHold(input);
  } catch (error) {
    ▼［新規］対象の制約違反だけを競合結果へ変え、それ以外は従来どおり呼び出し元へ返す
    if (error instanceof ExclusionViolation && error.constraint === "room_booking_claims_room_time_excl") return slotUnavailable();
    throw error;
  }
}
```

## テストは、設計と実行結果を分け、確かめられないことを書く

この題材ではテストを設計しただけで実行していないので、そう書いた。関数の単体テストでは、DBが同時要求を本当に拒否するかは確かめられないので、それも書いた。

> いずれもテスト設計の例で、実行結果はない。DBで同時要求を拒否できるかは、この関数の単体テストだけでは検証できない。

## 気になった点は、断定せず、確かめる方法と一緒に書く

制約名がドライバーから届くかは未確認なので、重大度を「要確認」にし、取り込み前に何を確かめるかを書いた。

> SQLSTATE `23P01`だけで判定すると、将来追加される別の排他制約の違反まで`SLOT_UNAVAILABLE`へ変換するおそれがある。取り込み前に、実DBへの重複書込みで制約名がこの関数まで届くことを確認する。
