# 図書館の貸出で今は扱わないこと

<!-- これは`deferred-scope`型の記載例である。**構成の基準資料ではなく、粒度と具体性の見本として読む。**架空の題材「図書館の貸出」の業務知識、ドメインモデル、論理データモデル、物理設計の見本が扱わないと決めたことを残している。 -->

図書館の貸出の業務知識、ドメインモデル、論理データモデル、物理設計は、本を借りる、返す、延滞にする、の三つだけを扱う。この資料は、四つの資料が扱わないと決めたことを一か所に残す。四つの資料はそれぞれの「未決」からこの資料を指し、この資料の中身を前提にはしない。窓口の担当者や開発者は、ここを読めば、延長や取り置きが「忘れられている」のではなく「今は扱わないと決めた」ことだと確かめられる。

## 将来の候補

### 貸出の延長

利用者が返却期限の前に、同じ本をもう一度同じ期間借りられるようにすることである。業務知識は「返却期限は借りた日の14日後で、貸出の間変わらない」を守っており、延長を認めるとこの決まりが崩れる。延長を認めるかどうかを図書館がまだ決めていないので、今は扱わない。

図書館が延長を認めると決めたら、最初に業務知識の決まりを直す。そのあとドメインモデルに返却期限を変えるコマンドを足し、論理データモデルに延長のイベントを足す。延長しても延滞の判定は新しい返却期限で行うので、延滞にする処理の読み取り（物理設計の Read-002）も見直すことになる。

### 本の取り置き

貸出中の本に、次に借りたい利用者が順番をつけておけるようにすることである。取り置きは貸出とは別に進む約束で、貸出が返されたときに次の人へ知らせる、という協調が要る。今の三つの行いだけでは利用者の不満が出ていないので、今は扱わない。

取り置きの要望が窓口に月10件を超えたら、考え直す。そのときは、取り置きを貸出とは別の集約として業務知識に書くところから始める。

## 採らなかった案

### 延滞のたびに延滞料を取る

延滞した日数に応じて利用者から料金を取る案である。この図書館では、延滞の貸出がある利用者には新しく貸さないことで、返却を促すと決めた。料金の計算と受け取りの業務が増えるわりに、返却が早まる根拠が無いため採らなかった。

市の条例で延滞料を取るよう求められたら、考え直す。

### 借りている冊数を貸出の表に列として持つ

利用者ごとの借りている冊数を列として保存し、貸出上限の判定で一行だけ読む案である。冊数は貸出中と延滞の貸出を数えれば出せる情報で、保存すると返すたびに二か所を直すことになる。一人の貸出は最大5行なので、数えても速さは足りる。物理設計はこの理由で採らなかった。

貸出上限の判定の読み取り（Read-001）が、目標の p95 5ms を実測で超えたら考え直す。

## まだ決まっていない値

延滞の通知には、仮に置いた値が三つある。どれも通知の送り先の応答時間が分からないと決められない。

| 値 | 今の扱い | 決める人 | 決まったら直す資料 |
|---|---|---|---|
| 回収のリース | 10分（仮） | 通知を運用する担当 | 論理データモデル、物理設計 |
| 回収を打ち切るまでの回数 | 5回（仮） | 通知を運用する担当 | 論理データモデル、物理設計 |
| 貸出上限の判定をやり直す上限 | 3回（仮） | 物理設計の担当 | 物理設計 |

リースと回数は、送り先が30秒以内に応答するという仮定から置いた。送り先を決める来月の打ち合わせまでに、応答時間の実測を持ち寄る。やり直しの上限は、貸出が一番混む土曜の午前の競合率を測ってから決める。
