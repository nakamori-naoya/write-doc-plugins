     ## 3つの不変条件

     1. **コアドメインの業務知識に限る。** 見出した知識を全部書く場所ではない。判定は1つの問いでできる。
        「作りを全部やめても残る決まりか」。残るなら書く。残らないなら書かない。
     2. **決まりを先、具体例を後。** 具体例より上の節で、ユビキタス言語・概念・常に守られること・
        状態の移り変わり・誰が行えるか・業務ルール・導出・同時に起きたとき・拒む理由を確定する。
        **具体例は資料の最後にまとめて置く。章のあいだに挟まない。**
        具体例より上だけを読んで業務の判断ができること。具体例に、上で書いていない決まりが
        現れないこと。現れたら、それは上の書き漏らしである。
     3. **業務の言葉だけを使う。** 常体（だ・である調）で書く。業務を知る人が使わない語は使わない。
        まとまりの代表・境界・属性の一覧といった作り手の語彙も使わない。

     ## 見出した知識をどこに書くか

     | 見出した知識                             | 書く場所                     |
     |------------------------------------------|------------------------------|
     | 業務で使われる対象・役割・状態の名前     | ユビキタス言語 > 業務用語   |
     | 起きたことで判断・状態・責任が変わる事実 | ユビキタス言語 > 業務イベント |
     | 業務上のまとまりと、その関係             | 概念                         |
     | いつでも破ってはならない決まり           | 常に守られること             |
     | 取りうる状態と、何が起きたら移るか       | 状態と、その移り変わり       |
     | 役割ごとに行える・行えない               | 誰が行えるか                 |
     | 操作ごとの成立条件・境界・拒む条件       | 業務ルール                   |
     | 条件から一意に決まるもの（計算・選び方） | 導出されること               |
     | 競合したときにどちらが通るか             | 同時に起きたとき             |
     | 拒む理由と、その根拠                     | 拒むときの理由               |
     | 上の決まりが具体の場面でどう働くか       | BDD（最後）                  |
     | 未確定の論点と、何が分かれば決まるか     | まだ決まっていないこと       |
     | 画面の作り・操作の手順                   | **書かない** → 画面の資料    |
     | 保存の形・仕組み同士のやりとり           | **書かない** → 設計の資料    |
     | 導入の背景・経緯・体制                   | **書かない** → 企画の資料    |
     | 検証の手順・確かめ方                     | **書かない** → 検証の資料    |
     | 他の業務が担うこと                       | **書かない** → その業務の資料|
     | 将来やるかもしれないこと                 | 「まだ決まっていないこと」へ1行だけ |

     **「なぜこの決まりなのか」は書く**（決まりの根拠）。
     **「なぜこの仕組みを作るのか」は書かない**（企画の理由）。背景を書きたくなったら、
     それは業務の決まりではない合図である。

     ## 図を使う場所

     文で読みにくいものだけを図にする。**mermaidで書き、画像を貼らない。**

     | 何を示すか                       | 使う図                          |
     |----------------------------------|---------------------------------|
     | 状態の移り変わり                 | `stateDiagram-v2`               |
     | 複数の担い手のやりとりと順序     | `sequenceDiagram`               |
     | ものの関係・分岐・流れ           | `flowchart`                     |

     **状態遷移は、何かが起きたから移る。** 矢印ラベルには必ず引き金（誰の操作か、何が届いたか）を
     書く。条件があれば `［...］` で添える。引き金の無い矢印を描かない。時間の経過だけで移るなら、
     それも「期限が来る」という引き金として書く。

     状態の節では、図の前に**引き金の一覧**を置くと、読み手が「何をすると何が動くか」を先に掴める。
     状態を持つものが複数あるなら、それぞれについて図を分ける。

     ## 迷ったときの判定

     | 迷い                       | 判定                                                       |
     |----------------------------|------------------------------------------------------------|
     | 決まりか、具体例か         | 「いつでもそうか」と言えるなら上の節。「このときはこう」なら具体例 |
     | 常に守られることか、業務ルールか | 誰が何をしても破れないなら前者。操作の可否の話なら後者     |
     | 業務ルールか、導出か       | 人が決めるなら業務ルール。条件から一意に決まるなら導出     |
     | 同時に起きたときか、作りの話か | 業務としてどちらが通るかを決めるなら書く。排他の方式が出たら書かない |
