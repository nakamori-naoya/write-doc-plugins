# 品質要求正本 — RoomFlow予約サービス

<!-- これは`quality-requirements`型の記載例である。**構成の正本ではなく、粒度と具体性の見本として読む。** RoomFlowは組織内の共用会議室を予約する架空のサービスであり、品質目標、調査結果、日付はすべて説明用である。 -->

**最優先の品質は、同じ利用枠に二件の成立予約を残さないことである。** 検索速度や通知時間は利用体験を左右するが、重複予約は会議室を利用できないという業務上の失敗を直接生む。そのため整合性だけを合意済み要求とし、応答時間、可用性、通知時間、検索反映時間は測定可能な仮説として検証する。事業責任者と設計者は、この正本で品質の優先順位と検証方法を合意する。繁忙期の停止を月間可用性へ含めるか（`QR-OQ-001`）と優先する通知経路（`REQ-OQ-001`）は未決なので、負荷試験は始められるが、正式なSLOと本番容量は確定しない。

## 対象と入力根拠

`REQ-002`と`REQ-003`は検索、予約、変更、取消を利用者が完了することを求めるため、利用者端末から結果が返るまでと、成立予約の状態を観測する。`REQ-001`は公開した利用枠が検索へ反映されるまでを、`REQ-004`は通知を受け取るまでを品質境界に加える。

試験時の入力は、`WL-001`の検索ピーク120件/秒、`WL-002`の予約系ピーク20イベント/秒、`WL-003`の通知ピーク60配送/秒、`WL-004`の利用枠更新ピーク8イベント/秒とする。いずれも`hypothesis`であり、実測値ではない。`REQ-OQ-001`が`open_question`のままなので、通知到達率の母集団は確定せず継続する。

## 品質要求

### QR-004: 重複した成立予約を常にゼロにする

同じ会議室の重なる利用枠に残る成立予約は、常に一件以下でなければならない。指標は重複成立件数、閾値は0件、対象は全予約枠である。`REQ-002`と`WL-002`を根拠とする`agreed_decision`であり、同じ利用枠への同時予約試験で検証する。

### QR-001: 検索結果の95%を800ミリ秒以内に返す

利用者端末が検索を送ってから結果を受け取るまでを観測し、成功した検索の95パーセンタイルを800ミリ秒以下とする。`WL-001`の120件/秒を10分与えて検証する。この閾値で離脱を抑えられるかは`QR-HYP-001`であり、品質要求自体の根拠状態も`hypothesis`である。

### QR-002: 予約系要求の月間成功率を99.9%以上にする

予約APIを外形監視し、予約、変更、取消要求の成功率を暦月で99.9%以上とする。`REQ-002`、`REQ-003`、`WL-002`を根拠とする`hypothesis`である。監視結果を月次集計するが、繁忙期障害の扱いは`QR-OQ-001`が決まるまで確定しない。

### QR-003: 通知の95%を60秒以内に届ける

予約の状態変更が確定してから、予約者または施設管理者の受信記録が残るまでを観測し、`WL-003`のピークが10分続く間も60秒以内の到達率を95%以上とする。これにより、通知キューへ入るまでの遅れと配送中の滞留をどちらも含める。`REQ-004`と通知許容時間の仮説を根拠とする`hypothesis`であり、状態変更の確定時刻と受信記録を照合して検証する。

### QR-005: 利用枠更新の99%を60秒以内に検索へ反映する

施設管理者が利用枠の公開または更新を受け付けられてから、予約者の検索結果へ現れるまでを観測する。`WL-004`の8イベント/秒が10分続く間、60秒以内の反映率を99%以上とする。`REQ-001`に基づく`hypothesis`であり、更新時刻と検索結果の時刻差で検証する。

## トレードオフと矛盾

### CONFLICT-001: 可用性目標と最大負荷の根拠がそろっていない

`QR-002`は月99.9%以上を求める一方、`WL-OQ-001`により年末繁忙期の倍率が分からない。必要容量と費用を比較できないため、事業責任者と運用責任者が前年実績と停止損失を確認するまで`open_question`とする。

### CONFLICT-002: 通知経路が未決のまま母集団を固定できない

`QR-003`は通知到達率を測るが、`REQ-OQ-001`が決まらなければ、メール、プッシュ通知、または両方のどれを測るか定まらない。事業責任者が経路を決めるまで、特定事業者の性能を品質要求へ混ぜない。
