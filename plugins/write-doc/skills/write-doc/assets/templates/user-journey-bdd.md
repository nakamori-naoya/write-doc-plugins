# <ユーザーの目的>のユーザー目的達成BDD

<!-- 執筆指示: 1人の主たるユーザーが、1つの目的を持って開始地点から最終地点へたどり着くまでを書く。道のりはいくつかの場面に分け、場面ごとに Given / When / Then で振る舞いを書く。この書き方をBDDと呼ぶ。この型を使うのは、User Journeyだと判定済みの対象だけである。
     書く: ユーザーの目的、開始地点、最終地点、完了条件、順番のある場面、場面から場面への接続、分かっている分岐、未決の点。
     目的は主たるユーザーの動機で決め、主たるユーザーが達成を観測できるかどうかで言い換えない。達成を観測できるのが受け手だけなら、受け手が観測する場面を置いてその When に受け手を立て、完了条件を受け手の観測で書く。主たるユーザー自身が観測できることは、その手前の場面の Then に書く。
     書かない: ドメインルールの網羅、データ構造、画面やAPIの操作手順、テストの実行環境や実行記録。
     冒頭は地の文の段落で始める。誰が何のために読むのか、どこから始まるのか、何が確かめられたら目的を達したと言えるのかを、その段落で書く。 -->

# 場面

<!-- 書く: 開始地点から最終地点までを、順番に分けた場面。ある場面の結果として、次の場面の前提へ渡る状態。
     場面と分岐には、主たるユーザーが見て分かる振る舞いだけを書く。迷ったら「この違いが起きたとき、主たるユーザーは何を見て気づくか」と問う。気づかない違いは書かず、書かなかったことへの断り書きも書かない。
     Whenで動く役割は、主たるユーザーと、主たるユーザーとやり取りする相手の役割に限る。通知基盤やバッチのようにシステムの中で動くものは、Whenに立てずにThenの結果として書く。
     Givenには、その場面のThenを変えうる前提だけを、値ごと書く。どの場面でも同じ形で効く制限は、それで結果が変わる失敗の場面にだけ値を書く。
     GivenもThenと同じく、主たるユーザーが観測できることか時間の経過で書き、仕組みの状態（反映されている、処理が済んでいる）を置かない。
     書かない: 目的と関係しない枝、前後とつながらない操作、UI部品、API、保存方法、テストの実行情報。 -->

## 場面 <連番>: <意味のある変化>

<!-- この見出しから「接続」までを、目的を達するのに要る場面の数だけ複製し、1から順に番号を付ける。見出しの名前には、その場面で何が変わるかを書く。
     最初の場面ではGivenに開始地点を書き、2つ目からは前の場面から受け取った状態を書く。
     どの場面にもGiven / When / Thenを必ず置く。Whenには、Thenを引き起こす業務上の行為か業務イベントを、一つだけはっきり書く。Thenには、見て分かる応答と、次の場面へ渡す状態を書く。
     失敗や拒否の場面は、成功の場面から確かめたい条件を一つだけ外して作る。そのThenのすぐ下に`NOTE: Rule:`を書き、別の資料で定めた規則なら`Source:`（相対Markdownリンク。業務知識の資料があればその資料、無ければ依頼の入力の要件の資料を指す）を、続けて`Reason:`を書く。「前提はこれで全部」と閉じる宣言や、書かずに共通だとみなす前提は置かない。
     書かない: 一つの場面に置いた複数の主な働きかけ、実装の手順、書かずに済ませた次の場面との接続。 -->
