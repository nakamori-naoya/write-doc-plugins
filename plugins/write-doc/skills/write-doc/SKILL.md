# write-doc

読み終えた読み手が、一つの判断または行動へ進めるMarkdown資料を1本作り、指定された保存先へ保存する。素材を集めること、関係者と合意すること、資料を公開すること、複数資料を編成することは別の仕事であり、素材が無ければ不足を返して止まる。

外部packageからは[公開契約](CONTRACT.md)の入力objectで呼ばれ、同じ契約の出力objectを直接返す。単独で依頼されたときも同じ入力へ整理してから始める。

## 入力

- `material`: 執筆の根拠。1件以上の配列で、各要素は `{kind: text, content: "..."}` か `{kind: file, path: /absolute/path}`。
- `document_type`: [`assets/template-examples.yml`](assets/template-examples.yml) にある型slug。任意。
- `output_directory` と `name`: 新規作成の保存先。`name` はpath要素を含まない `.md` 名。日本語名を含め文字種は制限しない。
- `update_target`: 更新する既存Markdownの絶対path。
- `references`: 追加で従う資料の絶対path配列。任意。

新規作成は `output_directory` + `name`、更新は `update_target` のどちらか一方だけを受け取る。契約に無いキー、空の `content`、相対path、読めないpath、未知の `kind` は入力不備として扱う。

## 判断基準

- **読み手と読後ゴールが素材に書かれているか。** 書かれていれば固定し、書かれていなければ推測せず一問で確認して止まる。
- **`document_type` が渡されているか。** 渡されていれば型カタログで解決してその型を使い、カタログに無いslugなら型を推測せず、利用可能なslug一覧を `reason` に含めて `failed` を返す。渡されていなければ読後ゴールを最も直接支える型を一つ選ぶ。二つ以上の型が同程度に該当して構成が変わるときは、候補と違いを示して一問で確認して止まる。
- **冒頭の段落は、読み手の既知の語で書いた本文か。** 誰が何を達成するために読み、どこから始まり、何が観測できたら完了かを最初の段落が文章として運ぶ。型・対象・確認日・確認した人のようなメタ情報の一覧や引用blockは冒頭に置かず、判断に要る事実（ADRの状態と決定者、PRの取込先と状態など）は文章の中へ置く。
- **型の読み方は資料の外にあるか。** Given / When / Thenの意味や表の読み方のような型の解説はtemplateのcommentと型カタログが担い、資料本文には書かない。ペルソナの知識段階は語の選び方の根拠にし、型解説を本文へ足す根拠にしない。
- **作業記録と正本を分けているか。** 中心の問い、扱う理由、確認日、確認した人、除外した候補は依頼元への報告や作業領域に残し、正本へ写さない。
- **保存先は依頼で示された構成か。** 保存先と名前は入力どおりに使い、既定の置き場を補わない。中間成果物は資料と同じ場所に作らず、保存するのは完成したMarkdownと、その資料が参照する最終版の画像・図だけである。
- **素材に根拠があるか。** テンプレートの節は論点の案内であり、素材に無い事実で空欄を埋めない。根拠が無い節は残さない。

## 手順

同じagentが、同じdirectoryの [`playbook.yml`](playbook.yml) が宣言する順で次を辿る。

1. **入力と保存先を検査する。** ファイル素材と `references` が読める絶対pathか、更新なら `update_target` が存在するMarkdownか、新規なら `output_directory` が書き込めるdirectoryで同名fileが無いかを確かめる。検査が終わるまでfileを作らず、更新もしない。
2. **読み手と読後ゴールを固定する。** [`references/core-principles.md`](references/core-principles.md) を読み、主な読み手と、読後にできる判断または行動を一つずつ定める。`references` があればここで読む。
3. **型と参考資産を選ぶ。** 型カタログ [`assets/template-examples.yml`](assets/template-examples.yml) からtemplateと記載例を解決して読む。templateが最終版のSVGを参照する型では、Markdownの保存名から `<名前から .md を除いたもの>.assets/` を同じdirectoryに割り当て、使うSVGごとに資産template、最終file名、Markdownからの相対pathを確定する。新規で同名資産があれば止まり、更新では同名資産の内容を読んで今回変えるSVGだけを対象にし、同じ資産directoryにある別のfileは変更も削除もしない。読み手の前提を判断する必要があれば `assets/personas/` から該当する一つを読む（backend-1 / backend-5 / pm-1 / pm-3 / product-user）。無ければ入力で明示された読者像だけを使う。
4. **構成を決める。** 冒頭で読み手の問いへ答え、その後は読後ゴールに必要な論点だけを依存順に並べる。呼び出し元が指定した見出しは保持し、それ以外のtemplateの節は判断または行動に必要な場合だけ残す。重要な前提、境界値、例外、未決は、それが判断を変える箇所の近くに置く。
5. **草稿を作る。** [`references/visuals-and-tables.md`](references/visuals-and-tables.md) を読み、本文・表・図の役割を分けてMarkdownをインメモリで組み立てる。文章は `core-principles.md`、表・図・コード・強調は `visuals-and-tables.md` の規律に従う。
6. **推敲を自己監査する。** [`references/integrity-check.md`](references/integrity-check.md) を読み、次の4点をすべて確かめてから保存へ進む。一つでも満たさなければ草稿へ戻る。
   - 読後ゴール照合: 冒頭だけで答えと対象範囲が分かり、各節が読後ゴールに必要な問いへ答えている。
   - 引き算: 削っても読み手の理解・判断・行動が変わらない記述を削り、重要な条件・反例・未決は残っている。
   - 事実と根拠の突合: 事実、数値、固有名詞、条件、リンクが素材と対応し、推定と未検証はその状態が書かれている。
   - 一文一意: 一文に一つのメッセージがあり、因果や条件の接続は壊れていない。
7. **保存して結果を返す。** 最終SVGがあれば先に保存し、次にMarkdownを保存する。更新では指定された変更範囲以外を保持する。保存後に読み直し、素材にない断定、重要条件の欠落、壊れたローカルリンク、未置換のplaceholderや執筆commentがあれば直して再確認する。確認できたら `status: completed` と絶対 `path` を返す。

## 停止条件

- 入力が契約を満たさない。違反項目を `reason` にして `status: failed` を返し、fileを変えない。
- `document_type` が型カタログに無い。型を推測せず、利用可能なslug一覧を `reason` に含めて `failed` を返す。
- 読み手、読後ゴール、型のいずれかを素材から一意に決められない。一問で確認して回答を待つ。
- 保存先または資産の保存先に同名fileがある（新規作成）。上書きせず `failed` を返す。
- 保存または読み直しに失敗した。部分的に保存されたfileの絶対pathを `reason` に含めて `failed` を返し、成功として扱わない。

## 出力

成功は `status: completed` と保存した `path`、失敗は `status: failed` と `reason` を、呼び出し元へ直接返す。1回の呼び出しで作る資料は1本だけである。
