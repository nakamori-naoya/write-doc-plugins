# 読み手情報の契約

文書型を選ぶ前に、読み手と読後の到達点を同じ記録へ揃える。値が確認できない場合は推測で確定せず、仮定または未確認として区別する。書き手と読み手は前提も経緯も共有しない状態を既定にする。

## 必須の記録

- `persona`: 同梱候補から選んだ主な読み手一人のファイルpath。仮に選んだ場合は、その根拠と仮定であることを添える。
- `reader_context`: 案件固有の語の知識段階、読む場面、起こりそうな誤解、到達点と、下記の4項目を含む読み手の前提。知識段階は `実務で使える`、`言われれば分かる`、`知らない` のいずれかにする。
- `goal_questions`: 本文だけを読んだ人が答えられる問いと、その `expected`（期待する答え）。2件から4件に絞る。1件では判断か行動の片方しか照合できず、5件以上は到達点が複数ある印として見直す。
- `open_questions`: 下記の形式で記録した未確認事項。
- `type`: 選んだ文書型のslug。
- `template`: 選んだ文書型に対応するテンプレートのpath。

## 未確認事項

`open_questions` は先頭に `count` を持ち、続く問いの件数と一致させる。問いが無い場合も `count: 0` を記録する。各問いは後から回答や決定と突き合わせられる形にする。

```yaml
count: 1
questions:
  - id: reader.goal.primary
    question: <確認する問い>
    recommended_answer: <現時点の推奨回答>
    consequence: <回答によって変わる判断または成果物>
```

`id` は記録中で一意かつ安定した識別子とし、英数字と `.` `_` `-` だけを使う。文言を直しても同じ問いならIDを変えない。`recommended_answer` には単なる「要確認」ではなく、現時点で妥当と考える回答を書く。`consequence` には回答の影響を受ける判断を具体的に書く。

含めるのは、読み手または到達点が依頼から決まらないことと、到達点の判断に必要だが素材に無い事実である。型の欄を埋めるためだけの不足、依頼が明示している事項、調べれば分かることは含めない。

## 読み手の前提

`reader_context` には次を記録する。

- `premises`: 主張が成り立つ条件のうち、読み手が知らないもの。素材の経緯から条件だけを取り出す。無ければ `前提は共有しない` とする。
- `stance`: 主張に対する読み手の初期態度。`初耳`、`賛成`、`反対`、`別案を持つ` のいずれかにし、確認できない場合の既定は `初耳` とする。
- `history`: `時系列で残す`、`前提へ畳む`、`書かない` のいずれかにする。文書型を決めた直後に、その型の既定を写す。文書型が無い場合の既定は `書かない` とする。
- `verification_means`: 読み手が根拠を確かめる手段。読み手のペルソナから決め、確認できない場合の既定は `リンクを開く` とする。

入力に確定済みの `decisions` がある場合、その値を仮定より優先する。入力間に矛盾があれば一方を選ばず、`open_questions` に残し、`count` に反映する。
