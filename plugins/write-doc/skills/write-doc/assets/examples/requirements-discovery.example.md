# 要件の見本（抜粋）

この見本は、要件の資料で判断が分かれやすい箇所だけを、会議室の予約サービスの題材から抜き出したものである。題材の値や言い回しは写さず、どこで何を判断したかを見る。節の構成はテンプレートが持つ。

## 具体的でも、根拠が仮説なら要求にしない

「通知は60秒以内なら待てる」は数字まで具体的だが、5人への聞き取りから置いた見立てで、決める人の合意が無い。だから要求ではなく仮説に置いた。決める人が対象と期限を指定して合意していれば、同じ文でも `REQ-` になる。変わるのは合意の有無で、文の具体性ではない。

> 「通知は60秒以内なら待てる」という見立ては、5人への聞き取りから置いた仮説である。品質目標として採用する前に、対象者と場面を増やして確認する。

| ID | 状態 | 後続で決める論点 |
|---|---|---|
| REQ-HYP-001 | hypothesis | 通知は60秒以内なら業務上許容されるか |
| REQ-OQ-001 | open_question | メールとプッシュ通知のどちらを優先するか |

## 導出要件は、特性から必要な成果までの因果で書く

入力に「同時予約を防げ」とは書かれていなかったが、人気の枠へ要求が集中するという特性と、電話台帳で起きていた重複から、避けるべき失敗が導ける。そこで因果を本文に書き、方式（ロックや制約の種類）は書かなかった。集中の度合いの値は利用負荷の資料が持つので、ここでは引くだけにする。題材が予約でなく配信なら、同じ形で「一つの操作の増幅を通常の利用者へ波及させない」のような成果になる。

> 人気の利用枠は公開直後に予約要求が集中する。電話台帳では同じ時間帯への重複予約が月12件起きていた。このため、空き状況の表示ではなく、予約を成立させる最終判断で重複を防ぐ必要がある。

## 手段は、固定制約か後続の候補に分ける

「既存のID基盤で認証する」は、事業責任者が範囲と時点を決めた必須の条件なので固定制約にした。通知の経路は、利用者の選択で方式が変わるので設計判断に入れず、後続で決める論点へ送った。同じ製品名でも、提案なら仮説、決める人が指定した必須なら制約になる。

| ID | 本文で扱う要求 | 根拠 |
|---|---|---|
| REQ-002 | 予約者が空いている利用枠を一件予約できる | 電話台帳の重複予約と事業責任者との合意 |
| DRV-001 | 同じ利用枠への同時要求で成立予約が一件を超えない | 電話台帳の重複予約 |
| CON-001 | 利用者認証を組織の既存ID基盤へ委ねる | 事業責任者との合意 |
