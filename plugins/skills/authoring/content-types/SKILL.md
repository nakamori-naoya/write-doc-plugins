# pick-content-type（読み手と到達点を決め、型を選ぶ）

**このスキルは文章を書かない。** **読み手を一人決め、読後の到達点を固定し、そこから型を1つ選ぶ**ところまでを担う。

**順序を入れ替えない。** 読み手 → 到達点 → 型である。型を先に決めると、型が持つ節を埋めるために内容を集めることになり、到達点に不要なものが入る。

**規律も媒体も知らない。** どう書くか・どう出すかは、それぞれ別の関心である。

## 0. 同梱物の root を決める

<!-- BEGIN shared:skill-entry/root-block -->
```bash
BUNDLE_ROOT="${CLAUDE_PLUGIN_ROOT:-/absolute/path/to/this/plugin}"
if [ -d "${BUNDLE_ROOT}/skills/authoring/content-types" ]; then
  PLUGIN_ROOT="${BUNDLE_ROOT}/skills/authoring/content-types"
else
  PLUGIN_ROOT="${BUNDLE_ROOT}"
fi
```

`PLUGIN_ROOT`は、この能力に同梱されたファイル群のrootを示す絶対パスである。実行環境から値が与えられない場合は、このファイルがあるdirectoryを明示する。
<!-- END shared:skill-entry/root-block -->

## 1. カタログを読む

<!-- BEGIN shared:skill-entry/config-load -->
```bash
CFG_FILE=$(bash "${PLUGIN_ROOT}/scripts/prepare.sh" "$(pwd)") || exit 2
printf '%s\n' "$CFG_FILE"
```

**このコマンドは説明例ではない。必ず実行する。** 解決済みYAMLが空なら先へ進まない。設定ファイルを直接読んで代用しない。

本文中の `${...}` は解決済みYAMLのプロパティである。使用時に `yq -er` で読み、欠落または `null` なら停止する。
<!-- END shared:skill-entry/config-load -->

`${.instructions.reader.directive}` と `${.instructions.selection.directive}` に従い、`${.catalog}` と `${.default_type}` を読む。

## 2. 読み手を一人決める

[ペルソナ](references/personas.md)の選び方で同梱5人から一人を選び、そのファイルpathを `persona` として記録する。

選んだペルソナを骨格として、この案件に固有の語がどの段階（実務で使える／言われれば分かる／知らない）にあるかを `reader_context` に書く。あわせて、主な読み手、読む場面、起こりそうな誤解、主張が成り立つ条件のうち読み手が知らないもの（`premises`）、主張への初期態度（`stance`）、根拠を確かめる手段（`verification_means`）を記録する。依頼と提供資料から分かる範囲を使い、推定は仮定と明示する。各項目は[読み手情報の契約](references/reader-input.md)に従う。

## 3. 読後の到達点を固定する

その読み手が読み終えた後にできるようになる判断または行動を書く。「理解する」で終わらせない。

到達点を、本文だけを読んだ人が答えられる問い2〜4個に落とし、期待する答えとともに `goal_questions` として残す。draft 工程が本文と照合する。

```yaml
goal_questions:
  - question: <本文だけで答えられる問い>
    expected: <期待する答え>
```

**この到達点が、以降すべての判断基準になる。** 不明点を洗い出すときも、節を置くか決めるときも、合否を決めるときも、ここへ戻る。読み手か到達点が依頼から決まらないことと、到達点の判断に必要で素材に無い事実を `open_questions` に残す。記録方法は[読み手情報の契約](references/reader-input.md)に従う。型の節を埋められないことは不明点にしない。

## 4. 型を決める

カタログの「選び方」を上から順に判定し、決まった型の詳細ファイル（`${.detail_dir}/<グループ>.md`）だけを読む。**選んだ型・slug・理由を1行で宣言する。** 呼び出し元が型を指定していれば、その型で書き、選び直さない。型が決まったら、カタログ「経緯の扱い」の型既定を `reader_context.history` に写す。

読み手か到達点が依頼から決まらない場合、対話できるなら依頼者へ聞く。対話せず処理する指定がある場合は `open_questions` に残す。読み手が未決のときは、ペルソナの選び方3で仮に選び、`persona` に仮定と記す。入力に確定済みの `decisions` があれば、仮定より優先する。

## 5. テンプレートと記載例を取る

`${.template_examples}` の `pairs.<slug>` にある `template` と `example` を、`${.plugin_root}` からの相対パスとして両方読む。slugはカタログの列をそのまま使う。対応が無い、パスが配布物の外を指す、ファイルが無い、のいずれかなら停止する。

**テンプレートは埋める枠ではない。** 節の候補と、各節の「書く／書かない」の境界を示す。節コメントと未置換のプレースホルダーは成果物から削除する。本文の構成は、ペルソナと到達点から作る経路表が決める。固定見出しを持つ型（カタログ）と、入力の成果契約で指定された見出し・順序だけを保持する。それ以外の節は、読み手の到達点に応じて省略・統合・並べ替える。省略・統合・並べ替えの理由は `reading_path` に残す。

必須の節に該当事項がないと確認できた場合は「なし」、情報不足は「未確認」と書き分ける。任意の節を埋めるための推測や枝葉の説明を足さない。判断に影響する未確認は省略せず本文へ残す。

テンプレートにある Mermaid のコードは図の候補として返す。文章本文を表す `body` には残さない。

**記載例は、粒度と具体性の見本であり、構成の正本ではない。** 節をどの粒度で切るか、図を何で描くか、具体例をどこまで具体的に書くかを読み取る。題材の中身は写さない。記載例を読む前に、到達点から必要な情報と暫定の経路を決めておく。先に例を読むと、例の節の集合をそのまま持ち込む。例を読んだ後に節を足すなら、その情報が無いと読み手はどの判断・行動ができないかを言えることを条件にする。

## 実行設定の寿命

prepareが返した絶対pathを実行記録へ保持する。別shellではそのpathを`CFG_FILE`へ明示して読み、shell変数の継承を前提にしない。完了時と失敗停止時のどちらも、最後の設定利用後に`python3 "${PLUGIN_ROOT}/scripts/run-config.py" cleanup --config "$CFG_FILE"`を実行する。他runの設定やdirectoryを削除しない。
