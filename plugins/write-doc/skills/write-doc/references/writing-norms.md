# 書くときの規範

この規範は、人が読む文章に共通する書き方である。write-doc が作る資料と、その型のひな形と見本だけでなく、SKILL.md のような指示の文も対象にする。書いてから直すより、書く前と書いている最中に縛るほうが効くので、草稿に入る前に読む。

規範は、すべての文に機械的に当てるルールではない。読み手が少ない手間で理解し、判断できるようにするための判断基準である。規範どうしがぶつかったら、読み手の得になるほうを選ぶ。

## 書く前に、主メッセージを一文で書く

本文に入る前に、この資料で読み手に一番伝えたいことを一文で書く。これを主メッセージと呼ぶ。一文で書けないときは、書き方ではなく素材が足りない。言い回しを工夫して埋めず、足りない素材を依頼元へ返す。

主メッセージが書けたら、次に見出しだけの骨組みを作る。見出しを上から順に読み、それだけで話が通るかを確かめる。通らなければ、本文を書く前に見出しの順番か中身を直す。本文を書いてから構成を直すと、書いた文を捨てることになるからである。

誰が読み、読んだ後に何を判断するか、何をするかも、ここで一つに決める。背景の説明は、その判断に要る範囲に絞る。ただし、なぜその課題があるのか、なぜその選択なのかという文脈は、読み手が納得するのに要るので削らない。

## 見出しには、その節の結論を入れる

「貸出」「概要」「処理」のような見出しは、中に何が書いてあるかを教えない。開いて中身を探す手間が大きい節ほど、その節の結論を見出しに入れる。図書館の貸出のドメインモデルなら、「## 貸出」より「## 貸出の境界は一冊の本に引いた」のほうが、開く前に判断が分かる。

全部の見出しを同じ書式にそろえない。どの見出しも同じ形の結論にすると、拾い読みが同じ調子の繰り返しになる。結論の文、問いの形、短いラベルを、中身に合わせて混ぜる。短い節や、名前だけで中身が分かる節はラベルのままでよい。

見出しは本文より強く言い切らない。本文が「未定」と書いていることを、見出しで決まったことのように書かない。

## 因果は地の文で書く

「返却期限を過ぎた」「延滞になった」「新しく借りられない」を箇条書きで並べると、三つの間の因果を読み手が組み立てることになる。「返却期限を過ぎても返さないと延滞になり、その利用者は新しく借りられなくなる」と地の文で書けば、書き手がその手間を引き受けられる。

段落は一つの話題でまとめ、冒頭の文で何の話かを示す。続く文は、その話題を理解するのに要る理由、条件、例を順に足す。別の話題に移るときは段落を分ける。

## 箇条書きと表は、使ってよい場面を決めておく

箇条書きを使ってよいのは、次の二つの場面だけである。それ以外は地の文で書く。

- 項目が互いに因果でつながらず、本当に並んでいるとき。担当と期日がそれぞれ違う作業の一覧がこれに当たる。
- 順序に意味がある手順を示すとき。

箇条書きは一段だけにし、入れ子にしない。項目の下に説明を続けたくなったら、その項目は小見出しを立てて本文で書く。

並列に見えても、見出しのすぐ下に箇条書きが三つ以上並んだら、項目の間に「だから」「ところが」で言える関係が隠れていないかを疑う。隠れていれば地の文に戻す。

表を使ってよいのは、同じ属性を持つ三つ以上のものを、読み手が行をまたいで比べるときだけである。セルには値か短い語を置き、判断や理由は入れない。なぜその値なのかは、表のすぐ後の本文で書く。道具が読む形として契約で決まった表は、行が三つ未満でもその形で書く。

## 読み手が知らない語は、何をするものかを先に言う

その語を、この資料の読み手が仕事の会話で使うかを考える。作り手の仲間内の略語、設計の中でだけ付けた名前、英語のままの専門語のように、読み手が使わない語は、何をするものかを平易に言ってから名前を渡すか、素直な言い方に置き換える。たとえば「一つのコマンドで一緒に守りたい決まりが届く範囲を、集約と呼ぶ」のように、働きを先に書き、名前を後に置く。名前を先に出すと、読み手はその語の意味を後の説明から逆にたどることになる。

語は、何を意味するかが具体的に分かるものを選ぶ。権威があることだけを示す語や、場面によって意味が揺れる語は、何を指すのか（業務知識の資料、判断の根拠、一次データ、再試行、同じ要求の繰り返しなど）を言う語に置き換える。「正本」「正式な定義」のように、どの資料の何を指すかが分からない語も同じである。

契約や規約で定義された語は、別の名前に言い換えない。同じものに名前が二つあると、読み手はそれが同じものかを確かめる手間を負う。そのかわり、その資料で初めて出るところで、何をするものかを一言で説明する。一度決めた名前は、資料の最後まで同じものに使う。

英語の一般語は、日本語として定着したカタカナで書く。ファイル、ディレクトリ、パス、ブロック、プレースホルダー、テンプレート、リポジトリ、スクリプト、コードがこれに当たる。前後に半角の空白は入れない。契約で定義された語（skill、playbook、package など）と、コードや設定に現れる識別子（`playbook.yml`、`document_type` など）は、元の綴りのまま書く。

## 翻訳調を避ける

英語の文の組み立てをそのまま移すと、文法は正しくても読みにくくなる。次の形を書いたら、ほかの言い方ができないかを考える。

物を主語にして他動詞で結ぶ文は、人か状況を主語に戻す。「この検査結果は、見本が古いことを示している」は「この検査結果から、見本が古いと分かる」にする。

「〜することができる」は可能形にする。「本を返すことができる」は「本を返せる」でよい。「〜することによって」は「〜して」「〜すれば」に、「〜という観点から」は「〜で見ると」にできることが多い。「〜を持つ」も、「〜がある」のほうが素直なことが多い。

名詞の前に修飾を何層も重ねない。「返却期限を過ぎても返されず、延滞の通知も届いていない、先月借りられた本」のように名詞に届くまで長いなら、文を二つ以上に割る。ダッシュで文の途中に説明を挟み込む書き方も、括弧にするか文を分ける。

## 語順と読点で、係り受けを迷わせない

長い修飾語を先に、短い修飾語を後に置く。節は句より先に置く。時と場所は、大きい枠から小さい枠へ書く。

読点は、文の構造の切れ目に打つ。長い修飾語が並ぶときはその境目に打ち、切れ目の無いところには打たない。息継ぎのための読点は、読み手に「何が区切られたのか」を探させる。

一つの文には一つのことを書き、主語と述語を近づける。ただし、因果や対比のように一つにつながった考えを、短くするためだけに細切れにしない。文と文の関係を読み手に推測させることになるからである。四十字から六十字は見直しの目安にすぎず、合否の基準ではない。

## 濃淡をつけ、同じ型を三回続けない

全部の節を同じ厚みと同じ文型で書くと、どこが大事かが伝わらない。判断を左右する節は例や数値を添えて厚く書き、言うことが少ない節は短く書く。書くことが無い見出しは置かない。

同じ型が三回続いたら、少なくとも一つは入り方を変える。型とは、「X は〜である」で始まる定義の文、節の中の並べ方（背景、仕組み、条件）、文の書き出しのことである。濃淡は強弱のことで、順番ではない。本当に並列なものに、優先順位を付けない。

## 確かさを言葉で書き分ける

事実は言い切る。推測には「と推定する」「仮に置く」のように推測だと分かる語を付け、確かめていないことには「未確認」と書く。全部の文を「と思われる」でぼかすと、どこが確かなのかが読み手に分からなくなる。

事実には、素材のどこにあるかが分かる参照を添える。素材に無いことを事実として書かない。素材にある事実を、一般的な知識や論理で読み手に分かるように説明するのは、書き足しではなく説明である。

## 削るのは、読み手の判断が変わらない記述だけ

書き手の身を守るためだけの注釈、中身の無い前置き、同じことの言い直しを削る。「本書では〜について述べる」のような書き出しは、何も伝えないので削る。

一方で、読み手が納得するための背景、仕組みの説明、判断を変える条件や例外、平易な言い換えや具体例は削らない。文字数を減らすこと自体を目的にしない。削った後に、判断に要る条件と根拠が残っているかを確かめる。

## 書き終えたら、見出しと段落の最初の文だけを読み返す

本文全体を読み直すと細部に気を取られ、構成の乱れを見落とす。見出しと各段落の最初の文だけを抜き出して、続けて読む。論旨が通るか、開く手間の大きい見出しに結論が入っているか、同じ型が三回続いていないか、節ごとに濃淡があるかを、この骨組みだけで確かめる。確かめられないなら、資料はまだ骨組みの段階で崩れている。
