# ポストモーテム: 同じ会議室の同じ枠へ2件の確定予約が成立した

> これは`postmortem`型の記載例である。**構成の正本ではなく、粒度と具体性の見本として読む。**架空の障害を、個人ではなく仕組みの因果として記録する。

- **発生**: 2026-08-27 10:02〜10:24（22分）
- **影響**: 予約者2名が同じ枠を確定し、1組が別室へ移動した
- **重大度**: SEV-2

## 何が起きたか

| 時刻 | 出来事 |
|---|---|
| 10:02:11.480 | 予約R-20260827-0311の仮押さえ要求を受け付けた（会議室M-301、9月18日 10:00から11:30まで） |
| 10:02:11.515 | 予約R-20260827-0312の仮押さえ要求を受け付けた（同じ会議室・同じ利用枠）。先の要求との差は35ms |
| 10:02:11.6 | 両要求とも空き確認で「空いている」と読み、どちらも仮押さえ予約として登録に成功した |
| 10:03 | 2件とも確定され、確認メールが2件送られた |
| 10:12 | 顧客から会議室運用責任者へ重複予約の連絡があった |
| 10:16 | 予約作成を一時停止した |
| 10:24 | 後着の予約R-20260827-0312を別の会議室へ移し、作成を再開した |

時刻はAPIのアクセスログの受付時刻である。35msはその2行の差であり、DB内で両transactionが空きを読んだ順序までは記録が無い。

## 根本原因

仮押さえ処理は空きの読取りと書込みを別々に行っていた。DBに同じ会議室の重なる時間範囲を拒む制約が無く、2つのtransactionがどちらも空きと判断して書込みに成功した。開始時刻だけの一意性では、開始時刻が異なる重複も防げなかった。

この結論は、重複した2件の予約レコードと、同じ会議室・重なる半開時間範囲を許したDB定義から判断した。**2つのtransactionが実際にどの順で読み書きしたかは未確認であり、上の説明はその範囲での仮説である。** 確かめるには、空き確認と登録の間に遅延を入れた2並列の再現手順で、制約の無い定義と有る定義の結果を比べる。担当者の確認漏れを原因とは扱わない。

## なぜ早く気づけなかったか

重複予約件数を計測しておらず、確定成功率の監視だけがあった。利用者からの連絡まで、業務上あり得ない組合せを検知できなかった。

## うまくいったこと

予約作成を会議室単位で停止できたため、全拠点停止を避けられた。丸の内店責任者が代替会議室を10分以内に確保できた。

## 再発防止

| 対策 | 種別（検知/防止/緩和） | 担当 | 期限 |
|---|---|---|---|
| 現在有効な予約枠占有へ会議室と半開時間範囲のGiST排他制約を追加する | 防止 | DB担当 | 2026-08-29 |
| 重複予約の検査を5分ごとに実行する | 検知 | SRE | 2026-08-30 |
| 排他制約違反`23P01`を`SLOT_UNAVAILABLE`へ変換する | 緩和 | API担当 | 2026-08-30 |

## 残っているリスク

既存データ全体の重複検査は完了していない。2026-08-29まで毎日検査し、重複があれば対象拠点の店舗責任者へ自動通知する。

今回の対策では、確定後の確認メールが遅れて届く問題は解消しない。通知の再送・抑止は別の変更として扱い、予約重複の防止対策へ混ぜない。
