# 文章スタイルガイド（既定）

**どういう語り口・粒度で書くか**の規約。差し替えたい場合は `.harness-plugins/writing-rules.config.yml` の `rules.style` に自分のファイルを指す。

## 日本語の読み手に通じる言葉を選ぶ

特に指定がなければ、日本語で読む日本人向けの文書として書く。使用言語や読み手が明示された場合は、その指定に従う。日本語が読めることと、その分野の知識があることは分けて考える。

- 広く使われる、意味の具体的な言葉を選ぶ。英語、カタカナ、略語だけでなく、難しい漢語や独自の言い回しも対象にする。難しい英語を難しい日本語に置き換えて済ませない。
- 「エンジニア向け」だけを根拠に、特定分野の専門用語を既知としない。依頼や資料から、その読み手が何を扱っているかを確かめる。不明なら一般的な開発知識を足場にし、分野固有の語は説明する。
- 専門用語が不要なら、具体的な動作や状態で言い換える。必要なら初出で平易な意味と、この文書で何を指すかを説明する。略語を英語の正式名称へ展開しただけでは説明にならない。
- 正確な区別に必要な語は残す。API名、コード中の名前、コマンド、画面のラベル、正式な製品名は照合できる表記を保ち、必要な説明を添える。読み手に定着している語へ毎回注釈を付ける必要はない。
- 同じ概念は同じ呼び名で追えるようにする。説明の途中で日本語・英語・略語を断りなく切り替えない。用語集だけへ説明を追い出さず、その語が理解に必要になる場所で意味が分かるようにする。

| 見直す表現 | この場面で伝える内容 |
|---|---|
| 「冪等性を担保する」（再試行の説明） | 「同じ要求を再送しても、予約が二重に作られないようにする」。性質の名前を扱う必要があれば、続けて「この性質を冪等性と呼ぶ」と説明する |
| 「オブザーバビリティを向上する」（調査方法の説明） | 「処理がどこで失敗したかを、ログなどから調べられるようにする」。元の語の全意味を置き換える定義ではなく、この文書で必要な内容を示す |
| 「当該機構の責務を把握する」 | 「この仕組みが何を担当するかを理解する」 |

## 語り口

- 常体（だ・である）で書く。
- 中身のない前置きを書かない。**1文目から中身を書く。**
- 断定できることは断定する。不確かなものは**何が不確かかを書く**。
- **確認していないことを確認したように書かない。**

## 文の粒度

**段落の割り方は `section` ガイドが決める。ここで決めるのは1文の長さと形である。**

- 結論を先に置く。理由は後ろ。
- **1文で言い切る主張は1つ。** 2つあるなら、そこが句点の位置である。
- **読点で節を3つ以上つながない。** 3つ目を足したくなったら切る。
- 1文は60字程度を目安にする。100字を超えたら、複数の主張、遠い修飾先、不要な反復を点検する。分割する場合も条件と結果の対応を保つ。字数だけで文を切らない。
- 独立した並列は箇条書き、同じ軸の比較は表を検討する。
- 理由や因果の展開は、つながりが伝わる文章にする。

### 文を伸ばす接続は、句点へ置き換える

接続で異なる主張を継ぎ足している場合は分割する。同じ条件と結果、原因と帰結を示す接続は、関係が明確なら保つ。次は見直しの候補であり、一律の置換規則ではない。

| 伸びる形 | 直し方 |
|---|---|
| 「〜であり、〜である」 | 前件で切る。対等な並列なら箇条書きにする |
| 「〜ため、〜である」「〜ので、〜である」 | 結論を1文で言い切り、理由を次の文へ回す |
| 「〜が、〜である」（逆接でない「が」） | 切る。逆接なら `section` ガイドの R10 に従う |
| 「〜として、〜する」「〜しつつ、〜する」 | 動作が2つある。2文にする |
| 「〜こと（もの）は、〜ことである」 | 名詞化をやめ、主語と述語のある文にする |

**主語が変わる連結は必ず切る。** 「A は B であり、C は D である」は2文である。1文へまとめると、読み手は主語をどこまで引き継ぐかを毎回判断させられる。

## 主語・対象・条件・述語を対応させる

**文章は、明示された文脈だけから「誰・何について、何を、どの時点・条件で、どうする／どうなる」が
一意に読めるように書く。** 文法上の主語や目的語をすべての文で機械的に反復するのではなく、意味上の
主体・対象・条件・述語の対応を曖昧にしない。

- 主語・対象・時点・条件を省略できるのは、同じ文、段落、見出し、列見出しから参照先が一意に決まり、
  別の解釈が生じないときだけである。
- 「これ」「同じ」「当日」「扱う」「返す」のような語だけでは主体・対象・結果が定まらない場合、
  具体的な主体名、対象となる値や状態、時点、結果を書く。
- 複数の主体・対象・時点を1つの文や行で扱う場合、それぞれと述語・結果の対応が分かるよう、名前を
  繰り返すか、文・箇条書き・表の列を分ける。
- 各文へ4要素をすべて詰め込む必要はない。その文が述べる関係を、読み手が暗黙の主語や目的語を
  推測せず一意に復元できることを合格条件にする。

この一般則は、仕様、設計、受け入れ条件、具体例にもそのまま適用する。Given/When/Thenは1シナリオ内で
主体・対象・条件・結果の対応を閉じ、別シナリオの暗黙情報を引き継がない。表は列見出しと各行だけで
対応が分かるようにし、前の行や空欄セルを補って読ませない。

## 流し読みへの対応

読み手が必要箇所だけを読む場合にも、判断の条件が落ちないようにする。

- **最も重要な情報を冒頭に置く。** ゴールをタイトルに要約し、最初の3段落に要点を入れる。
- 長い塊を割る。見出し・リスト・コールアウトで、流し読める形にする。
- 見出しだけを追って筋が通るようにする。

## 手順の書き方

- **1手順1行動。** 2つの動作を混ぜない。
- 手順ごとに期待結果を書く。
- 手順が10を超えたら、分割するか、対象が複雑すぎないかを疑う。

## 避けること

- 章立てのために内容を薄めること
- 読み手が違う内容を1本に混ぜること
- 「〜と思われる」で断定を避けること
- 秘匿（トークン・PII・マシン固有パス）を載せること
