# write-doc 公開契約 v2

`write-doc` は、渡された素材から Markdown 資料を1本作り、明示された保存先へ保存する。

| 項目 | 値 |
|---|---|
| 契約 ID | `write-doc/write-doc` |
| 版 | `2` |
| kind | `playbook` |
| playbook | `write-doc` |
| marketplace / plugin | `write-doc` / `write-doc` |

## 入力

| 名前 | 必須 | 型 | 意味 |
|---|---|---|---|
| `material` | 必須 | object[] | 本文の根拠にする素材。下記の要素を1つ以上 |
| `document_type` | 任意 | string | 型の一覧（`assets/template-examples.yml`）にある文書型の名前。省略時は目的に合う型を選ぶ |
| `output_directory` | 条件付き | 絶対パス | 新規作成先。`name` と組み合わせる |
| `update_target` | 条件付き | 絶対パス | 更新する既存 Markdown ファイル |
| `name` | 条件付き | string | 新規作成する `.md` ファイル名 |
| `references` | 任意 | 絶対パスの配列 | 追加で従う資料 |

新規作成では `output_directory` と `name` を両方渡す。更新では `update_target` を渡す。両方式を同時に渡さない。保存先を省略した入力は失敗とし、write-doc は保存先を推測しない。

`material` の各要素は、インライン素材なら `{kind: text, content: "..."}`、ファイル素材なら `{kind: file, path: /absolute/path}` とする。空の `content`、相対パス、読み取れないパス、未知の kind やキーは受け付けない。この区別により、存在しないファイルパスを文章として扱わない。

`references` は読み取り可能な絶対パスでなければならない。プロジェクト固有の規約や文脈は、対象リポジトリのAGENTS.md / CLAUDE.mdと `references` で渡される。`update_target` は `.md` ファイルでなければならない。`name` はパス要素を含まない `.md` ファイル名とする。表にない入力キーは受け付けない。`document_type` が渡された場合は選び直さない。

## 出力

成功:

```yaml
status: completed
path: /absolute/path/to/document.md
```

失敗:

```yaml
status: failed
reason: 保存できなかった理由
```

| 名前 | 条件 | 型 | 意味 |
|---|---|---|---|
| `status` | 常時 | `completed` または `failed` | 実行結果 |
| `path` | 成功時 | 絶対パス | 保存して確認した Markdown 資料 |
| `reason` | 失敗時 | string | 停止理由 |

出力は呼び出し元へ直接返す。中間 YAML や出力 YAML は作らない。1回の呼び出しで作る資料は1本だけである。

## 保証

- 素材、追加参照、確定済みの文書型を執筆に反映する。
- `update_target` を渡した場合だけ既存ファイルを更新する。
- 新規作成先に同名ファイルが存在する場合は上書きせず失敗する。
- 完成した Markdown と、その資料から参照する最終版の画像・図以外の中間成果物を作らない。
- 保存と整合性確認を完了した場合だけ `completed` を返す。

## 公開する資料

ほかの package が読んでよい資料は、次の一つだけである。

| 名前 | 場所（この公開入口のディレクトリからの相対パス） | 目的 |
|---|---|---|
| 書くときの規範 | `references/writing-norms.md` | 人が読む文の書き方の基準。write-doc が作る資料だけでなく、ほかの package の SKILL.md や資料も、文の書き方はこの規範に従ってよい |

この資料の名前と場所は、契約の版2の間は変えない。変えるときは契約の版を上げる。消費側は、名前と場所で指すだけにし、中身を写したり、節の名前に依存したりしない。

これ以外の工程、内部 skill、テンプレート、参照文書、実装用スクリプトは非公開であり、消費側は参照しない。

## 検査が読む目印

ほかの package の検査スクリプトが write-doc の資料から読んでよいのは、この節が文書型ごとに宣言した目印だけである。目印は、図の記法、ID、決まった形の表の見出し行、見出しの先頭に置く名前のように、書き手が中身の結論とは別に置く印である。見出しの文言は目印にしない。だから見出しには、書くときの規範に従って節の結論を入れてよい。目印を変えるときは契約の版を上げる。

### north-star と strategy

節は H2 見出しで置き、見出しの最初の半角 `:` より前を節の名前にする。`:` の後ろには節の結論を書いてよい。north-star は `対象`、`望む状態`、`約束する価値`、`プロダクトの役割`、`判断原則`、`やらないこと`、`根拠と仮説`、`見直し条件`、`未決` の九つの節を、この順に一つずつ置き、どの節も空にしない。north-star には、`診断`、`基本方針`、`一貫した行動`、`資源配分`、`行動計画`、`ロードマップ`、`期限つき施策` を名前にした節を置かない。strategy は `診断`、`基本方針`、`一貫した行動` の三つの節を、この順に一つずつ置き、どの節も空にしない。

### domain-rule

ユビキタス言語は、見出し行が `| 業務の言葉 | 英名 | 種類 |` の表に1語1行で置く。種類は `業務用語`、`業務イベント`、`概念`、`コマンド`、`クエリ` のどれか一つで、一つの語は一つの種類にだけ置く。業務用語でもある概念は `業務用語` として置く。

状態を持つものごとに、状態遷移図を1行目が `---` の Mermaid ブロックで描く。ブロックの先頭は `---`、`title: <状態を持つもの>`、`---` の三行で、その次の行が `stateDiagram-v2` である。遷移の行は `<状態> --> <状態>: <業務の行い>` にし、生成は `[*]` から始め、終端は `--> [*]` で閉じる。状態名がその状態の正式な名前になる。

BDD は `### [BDD-<3桁以上の数字>] <業務結果>` の見出しで一件ずつ置く。

### domain-model

クラス図は、1行目が `classDiagram` の Mermaid ブロックで描く。クラスは `class <英字の識別子>["<ラベル>"]` で宣言し、波括弧の中に種別を `<<集約ルート>>`、`<<エンティティ>>`、`<<値オブジェクト>>`、`<<ドメインイベント>>` のどれか一つで書く。ほかの文脈でも使う値の種別には `・文脈共有` を添える。集約ルートとエンティティの中は、種別のほかに `+<コマンド名>(<引数のラベル>, …)` の行だけを置き、引数には同じ図のクラスのラベルを書く。値オブジェクトの中は括弧を含まない語の行だけ、ドメインイベントの中は種別だけにする。関係の線は、宣言したクラスの識別子どうしを結ぶ。

状態遷移図は、1行目が `stateDiagram-v2` の Mermaid ブロックで描く。行は `<状態> --> <状態>: <コマンド名>` だけにし、生成は `[*]` から始め、終端は `--> [*]` で閉じる。ラベルを省けるのは終端への矢印だけである。一つの図の矢印のラベルは、一つの集約ルートのコマンドだけにする。この図を含む H2 節が、その集約の節になる。一つの集約の状態遷移図は一つの H2 節に置き、一つの H2 節には一つの集約の状態遷移図だけを置く。

状態遷移図で矢印の出ていない状態があるコマンドの拒む理由は、その集約の節の中の H3 に書く。この H3 は、見出しの最初の半角 `:` より前をコマンド名にする。`:` の後ろには結論を書いてよい。

本文が引く BDD は `BDD-<3桁以上の数字>` で書き、範囲は `BDD-001〜004` のように書く。

### rdb-logical-data-modeling と rdb-physical-design

論理データモデルは、すべての論理テーブルを、見出し行が `| 系列 | 性質 | 論理テーブル | 保存表現 | 時刻 | 変化 | 根拠 |` の表（分類の表）に1テーブル1行で置く。テーブル名は backtick で囲む。すべてのテーブルと列は、1行目が `erDiagram` の Mermaid ブロックに描き、属性は `<型> <名前> [PK|FK|UK] "<意味>"` の行にする。テーブルごとの定義は、`### ` の直後に backtick で囲んだテーブル名を置いた見出しで始める。名前の後ろは自由に書いてよい。業務制約は `#### 業務制約: <制約名>` の行で書く。物理設計の検査は、erDiagram の実体と属性の行と業務制約の名前から、論理構造の指紋を計算する。

物理設計は、次のラベルの行を一行ずつ置く。`- 対象DBMS: <製品名>`、`- 対象バージョン: <版>`、`- 論理モデル: <論理データモデルのファイル名を含む>`、`- 論理構造の指紋: sha256:<検査が計算した値>`、`- 要求資料:`、`- 利用・負荷モデル:`、`- 品質要求資料:`、`- 基盤構成資料:`、`- 検証証拠:` である。

物理設計の表は、見出し行が次の形のものを一つずつ置く。物理制約は `| 制約名 | 対象 | 実現方法 | 適用時点 | 違反時の扱い |` で、制約名の集合を論理データモデルの業務制約の名前の集合と一致させる。index は `| index | 対象 | 種類 | 支えるRead・更新 | 更新費用 | 検証状態 |`、代表的な読み取りは `| Read | 利用者 | 並び順と上限 | 鮮度と一貫性 | 想定件数 | SLO | 支えるindex |` で、Read の名前は `Read-<3桁以上の数字>` にする。支える Read と支える index は、互いの表にある名前で書き、支える index が無い Read には `なし` と書く。

物理設計の小見出しは、先頭の名前で種類を示す。`### 分離性判断: <判断名>` は本文に `検証状態: <verified か planned>` の行を一つ置く。`### 機能: <機能名>` は `- 利用可能な版:`、`- 根拠:`（`https://` か `local:` で始める）、`- 検証状態:` の行を一つずつ置く。`### 検証: <名前>` は `- 状態: <verified か planned>` の行を一つ置く。物理設計には BDD（`### Scenario`、行頭の `Given`、`When`、`Then`、`And`）を写さない。

### requirements-discovery、workload-model、quality-requirements、cloud-architecture

ID は `<接頭辞>-<3桁以上の数字>` で書く。仮説は `<接頭辞>-HYP-<数字>`、未決は `<接頭辞>-OQ-<数字>` で、接頭辞は要求発見が `REQ`、利用負荷が `WL`、品質が `QR`、クラウド構成が `ARC` である。構成図のノードは `NODE-<英大文字と数字>` で書く。根拠の状態は `fact`、`agreed_decision`、`hypothesis`、`open_question` の値をそのまま書く。

後続の資料が ID で指すものは、見出し行が次の形の表（追跡の表）に1行ずつ置く。追跡の表は、どの見出しの下に置いてもよい。一つのセルに複数の ID を書くときは `、` で区切る。

requirements-discovery は、`| ID | 本文で扱う要求 | 根拠 |` の表に REQ-、DRV-、CON-、DEC- を置き、仮説と未決があれば `| ID | 状態 | 後続で決める論点 |` の表に REQ-HYP- と REQ-OQ- を置く。workload-model は `| ID | 設計入力 | 根拠と状態 | 影響する要求・判断 |`、quality-requirements は `| ID | 守る性質 | 観測・検証 | 根拠と状態 |` の表に置く。cloud-architecture は `| ID | 内容 | 根拠と状態 |` の表に、CON-、NODE-、ADR-、FAIL-、ARC-HYP-、ARC-OQ- と、上流から引き継いだ仮説と未決を置く。「根拠と状態」のセルには状態の値を一つと、根拠にした ID を書く。

cloud-architecture の構成図は、1行目が `flowchart` で始まる Mermaid ブロックを資料に一つだけ置き、追跡の表のすべての NODE- を表示名に含める。

用語定義を参照する資料は、`用語定義: <絶対パス> 版: <整数>`（参照しないなら `用語定義: なし`）の行を一つ置き、続けて `推奨用語名: <名>、<名>` の行を置く。コマンドとクエリの操作を並べるときは、見出し行が `| 操作 | 種別 |` で始まる表に置き、種別を `コマンド` か `クエリ` にする。

これらの資料をほかの資料の上流として読むときは、表の1列目と、`### <ID>: ` で始まる見出しの ID を、その資料が定義した ID とみなす。
