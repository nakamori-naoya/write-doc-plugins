# write-doc

渡された素材から、読み手が読み終えたら一つの判断か行動へ進めるMarkdown資料を1本書き、指定された場所へ保存する。素材を集める、関係者と合意する、資料を公開する、複数の資料をまとめて組む、という仕事はしない。素材が足りなければ、足りないものを返して止まる。

ほかの package からも、人から直接頼まれたときも、下の入力の形に整理してから始め、出力の形で結果を返す。ほかの package が読んでよいのは、書くときの規範（[`references/writing-norms.md`](references/writing-norms.md)）と、各型のテンプレートの冒頭にある「検査が読む目印」だけである。目印は見出しの文言から切り離してあるので、見出しには節の結論を入れてよい。目印を変えるときは、それを読む検査の持ち主と同時に変える。

## 入力

- `material`: 本文の根拠にする素材。1件以上の配列で、各要素は `{kind: text, content: "..."}` か `{kind: file, path: /absolute/path}` である。
- `document_type`: 文書型の名前。[`assets/template-examples.yml`](assets/template-examples.yml) に載っている名前を使う。省略してよい。
- `output_directory` と `name`: 新しく作る資料の保存先とファイル名。`name` は `/` を含まない `.md` の名前で、日本語も使える。
- `update_target`: 書き直す既存のMarkdownの絶対パス。
- `references`: 追加で従う資料の絶対パスの配列。省略してよい。対象のリポジトリの置き場、命名、文体の決まりは、そのリポジトリの AGENTS.md や CLAUDE.md と、この入力で渡される。

新しく作るなら `output_directory` と `name`、書き直すなら `update_target` の、どちらか一方だけを受け取る。この形に無いキー、空の `content`、相対パス、読めないパス、知らない `kind` は、入力の不備として扱う。

## 判断基準

### 読み手と、読んだ後に何をするかは素材に書かれているか

書かれていれば、そのまま使う。書かれていなければ、依頼の文、素材の宛先や言葉づかい、文書型から、最も筋の良い読み手と、読んだ後の判断か行動を一つ選ぶ。選んだものは仮に置いたものとして、根拠と、選ばなかった候補を添えて報告する。素材に無い事実を、仮に置く根拠にしない。

### 文書型は渡されているか

渡されていれば、型の一覧でその型のテンプレートと見本を引く。一覧に無い名前なら型を推測せず、使える名前の一覧を `reason` に入れて `failed` を返す。渡されていなければ、読んだ後の判断を最も直接支える型を一つ選ぶ。二つ以上の型が同じくらい当てはまるときも止まらない。一つを仮に選び、候補と違いを報告に添えて、利用者が資料を見てから選び直せるようにする。

### 冒頭の段落は、読み手が知っている言葉で書いた本文か

誰が何のために読むのか、なぜその判断や課題があるのか、どこから始まり、何が見えたら終わりなのかを、最初の段落が文章で運ぶ。型、対象、確認した日や人の一覧や引用のブロックは、冒頭に置かない。判断に要る事実（ADR の状態と決めた人、PR の取り込み先と状態など）は、文章の中に書く。

### 型の読み方を本文に書いていないか

Given / When / Then の意味や表の読み方のような、型そのものの説明はテンプレートの注釈と型の一覧が受け持つ。資料の本文には書かない。読み手の知識の段階（`assets/personas/`）は言葉を選ぶ根拠に使い、型の説明を本文に足す根拠にはしない。

### 作業の記録と成果物を分けているか

何を問いにしたか、なぜ扱うか、確認した日や人、外した候補は、依頼元への報告に書き、成果物には写さない。

### 保存先は依頼のとおりか

保存先と名前は入力のとおりに使い、決まった置き場を勝手に補わない。途中の作業ファイルは資料と同じ場所に作らない。保存するのは、完成したMarkdownと、その資料が参照する最終版の画像と図だけである。

### 素材に根拠があるか

テンプレートの節は、論点を思い出すための案内である。素材に無い事実で空欄を埋めない。根拠の無い節は置かない。素材にある事実を、一般的な知識や論理で読み手に分かるように説明するのは、書き足しではなく説明である。

## 手順

1. **入力と保存先を確かめる。** ファイルの素材と `references` が読める絶対パスかを確かめる。書き直しなら `update_target` が既存のMarkdownか、新しく作るなら `output_directory` に書き込めて同じ名前のファイルが無いかを確かめる。確かめ終わるまで、ファイルを作らず、書き換えもしない。
2. **読み手と、読んだ後の判断を決める。** [`references/writing-norms.md`](references/writing-norms.md)（書くときの規範）を読み、主な読み手と、読んだ後にできる判断か行動を一つずつ決める。`references` があればここで読む。
3. **型と見本を選ぶ。** 型の一覧 [`assets/template-examples.yml`](assets/template-examples.yml) からテンプレートと見本を引いて読む。見本は粒度と具体性の見本であり、見出しと構成はテンプレートとこの手順で決める。見本の題材、値、太字の置き方のような書式の癖は写さない。テンプレートが最終版のSVGを参照する型では、保存名から `.md` を除いた名前に `.assets/` を付けたディレクトリを、同じ場所に割り当てる。使うSVGごとに、元にするテンプレート、最終のファイル名、Markdownからの相対パスを決める。新しく作るときに同じ名前の資産があれば止まる。書き直すときは同じ名前の資産を読み、今回変えるSVGだけを書き換える。同じディレクトリのほかのファイルは変えも消しもしない。読み手の前提を見極める必要があれば、`assets/personas/` から一人を読む（backend-1、backend-5、pm-1、pm-3、product-user）。当てはまる人がいなければ、入力で示された読み手の像だけを使う。
4. **主メッセージと骨組みを決める。** 書くときの規範の「書く前に、主メッセージを一文で書く」に従い、主メッセージと見出しだけの骨組みを作る。主メッセージを書けなければ、足りない素材を返して止まる。呼び出した側が指定した見出しは残し、それ以外のテンプレートの節は、判断か行動に要るときだけ残す。
5. **草稿を書く。** [`references/visuals-and-tables.md`](references/visuals-and-tables.md) を読み、Markdownを手元で組み立てる。文章の書き方はすべて書くときの規範に、表、図、コード、強調の受け持ちは `visuals-and-tables.md` に従う。テンプレートの執筆指示は、その型に何を書くかを決めるもので、書き方の判断は規範に任せる。
6. **自分で読み直して直す。** [`references/integrity-check.md`](references/integrity-check.md) で素材との照合と資料の中の食い違いを確かめ、書くときの規範の「書き終えたら、見出しと段落の最初の文だけを読み返す」で骨組みを確かめる。どちらかで欠けが見つかれば草稿に戻る。
7. **保存して結果を返す。** 最終版のSVGがあれば先に保存し、次にMarkdownを保存する。書き直しでは、頼まれた範囲の外を変えない。保存したら読み直し、素材に無い断定、大事な条件の抜け、切れたリンク、残ったプレースホルダーや執筆の注釈があれば直して、もう一度確かめる。確かめられたら `status: completed` と絶対 `path` を返す。

## 止まるとき

次のときは止まり、`status: failed` と `reason` を返す。成功として扱わない。

- 入力が上の形に合わない（知らない key、空の `content`、相対パス、読めないパス、知らない `kind`、保存先の二つの方式が混ざっている、どちらも無い）。どこが合わないかを `reason` に書き、ファイルを変えない。
- 文書型が型の一覧に無い。型を推測せず、使える名前の一覧を `reason` に入れる。
- 新しく作る資料か資産の保存先に、同じ名前のファイルがある。上書きしない。
- 主メッセージを一文で書けるだけの素材が無い。足りないものを `reason` に書く。
- 保存か読み直しに失敗した。途中まで保存したファイルがあれば、その絶対パスを `reason` に入れる。

次のときは止まらず、仮に置いたものを示して進める。

- 読み手、読んだ後の判断、文書型（`document_type` が無いとき）が素材から一つに決まらない。判断基準のとおりに最も筋の良い一つを仮に置いて書き、仮に置いたこと、根拠、選ばなかった候補を報告に添える。
- 根拠の無い節がある。空欄を埋めず、その節を置かない。素材の記述が推測や未確認なら、そうだと本文に書く。

## 出力

成功なら `status: completed` と保存した `path` を、失敗なら `status: failed` と `reason` を、呼び出した側へそのまま返す。仮に置いた読み手、読んだ後の判断、文書型があれば、結果の外の報告に、根拠と選ばなかった候補を添える。1回の呼び出しで作る資料は1本だけである。
