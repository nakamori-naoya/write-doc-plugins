# コンテンツタイプのカタログ

**型は飾りではなく、読み手と目的の宣言である。** 型を決めずに書くと、読み手の違う内容が1本に混ざり、誰にとっても長くて使えない文書になる。

コンテンツタイプの分類と名称は『エンジニアのためのドキュメントライティング ユーザーの問題解決とプロダクトの成功を導く』（ジャレッド・バーディ ほか著／岩瀬義昌 訳／[日本能率協会マネジメントセンター](https://pub.jmam.co.jp/book/b622627.html)／2023年3月／ISBN 978-4-8005-9083-1、原書 *Docs for Developers*）から借りている。**逐語の引用は含まない。** そこに無い、現在の開発現場で常用される型（**ADR・デザインドック・ポストモーテム・Runbook・リリースノート**）を足してある。

## 選び方（この順で判定する）

```
0. 読み手は「いま何がどうなっているか」を追いたいか
     期間内の動きを一望したい      → 期間ダイジェスト
     決まったことだけ追いたい      → 決定ログ
     決まっていないことを追いたい  → 論点台帳
0.4 読み手はプロダクトの方向または経路を決めたいか
     長期の価値ある未来と判断基準を揃えたい → Product North Star
     現在地から課題、方針、行動を選びたい   → Product Strategy
0.5 読み手は「業務として何が正しいか」を確定したいか → 業務知識・コアドメイン
0.55 読み手は「ユーザーが目的を達成するまで」を端から端まで共有したいか → E2E BDDシナリオ
0.6 読み手は「業務のデータをどう永続化するか」を決めたいか
     業務シナリオからRDBへ記録する事実と論理構造を決めたい → RDB論理設計
     固定済みの論理構造を対象RDBへ写したい          → RDB物理設計
1. 読み手は「困っている」か        → はい: トラブルシューティング
2. 読み手は「決定の理由」を知りたいか → はい: ADR（決定済み） / デザインドック（検討中）
3. 障害・事故の振り返りか           → はい: ポストモーテム
4. 読み手の目的は明確か
     その1件を片付けたい            → ハウツーガイド
     決まった作業を正確に反復したい  → Runbook
5. 読み手は初見か
     まず動かしたい                → スタートガイド
     体系的に学びたい              → チュートリアル
     組織・全体像から入る          → オンボーディング
6. 動かせるが理解が足りないか       → コンセプトドキュメント
7. 使用中に値・仕様を引きたいか     → リファレンス / 用語集
8. 変更点を知らせたいか            → リリースノート
9. リポジトリの入口か              → README / コードコメント
9.3 既存コードを説明したいか
     どこに何があるかを渡したい    → コード地図（マクロ）
     特定の処理を実行順に追わせたい → コードリーディング
9.5 特定の変更（PR）を説明したいか → 実装解説（PR）
10. 行き先へ振り分けたいか          → ランディングページ
```

**迷ったら「読み手が今どこにいるか」で決める。** 手を動かす前か、動かしている最中か、動かした後か、動かせなくなったか。

**0.5 番も性質が違う。** ほかが「作ったものを説明する」型なのに対し、これは**作る前から在って、作りが変わっても変わらない業務そのもの**を残す型である。実現手段が1文でも混ざったら、それは別の型の内容である。

**0 番だけは性質が違う。** 1〜10 は「読み手を、ある理解や状態へ連れていく」型だが、0 番の3種は**散らばった事実を状態順に並べ直す**型である。読み手はすでに文脈を持っていて、教えられたいのではなく**追いたい**。会議・議事録・チャットのような一次資料から起こすときは、まずここを見る。

| **Product Strategy** | `strategy` | 資源配分と行動を決める人 | North Starはあるが、現在地から何へ集中するかが決まっていない | 診断、基本方針、一貫した行動の因果を結ぶ | [detail/product.md](detail/product.md) |
| **業務知識・コアドメイン** | `domain-rule` | 業務を知る人と、それを形にする人 | 決まりが人によって違って伝わっている | **業務として何が正しいか**を確定させる | [detail/domain.md](detail/domain.md) |
| **E2E BDDシナリオ** | `e2e-bdd-scenarios` | ユーザーの目的達成を共通理解にする人 | 個々の振る舞いは分かるが、開始から目的達成までが一続きに説明できない | ユーザーの目的、開始地点、インタラクション、最終地点を一続きのBDDストーリーにする | [detail/e2e-bdd.md](detail/e2e-bdd.md) |
| **RDB論理設計** | `rdb-logical-data-modeling` | 業務を知る人と、RDBへデータを永続化する人 | 何を記録すべきか説明できない | CUDの業務シナリオから記録する事実と論理構造を決める | [detail/data-modeling.md](detail/data-modeling.md) |

| **ハウツーガイド** | `how-to` | 目的が明確な人 | 手段を知らない | その課題だけを解決させる | [detail/learning.md](detail/learning.md) |
| **コンセプトドキュメント** | `concept` | 理解したい人 | 動かせるが、なぜかが分からない | 裏側の考え方を理解させる | [detail/learning.md](detail/learning.md) |
| **オンボーディング** | `onboarding` | 新規参加者 | 全体像も文化も知らない | 自走できる状態まで立ち上げる | [detail/learning.md](detail/learning.md) |

## 混ぜてはいけない組み合わせ

| やりがち | なぜ壊れるか | どうするか |
|---|---|---|
| Product North StarとProduct Strategyを1本にする | 長期の方向と現在地からの経路では読み手の判断が違う | 2つの型へ分ける |
| 業務知識と実装説明を1本にする | 業務上の正しさと作りの説明では更新理由が違う | 業務知識と適切な実装文書へ分ける |
| E2E BDDシナリオにdomain-ruleやdata modelを混ぜる | 目的達成のストーリーと個別の決まり・保存構造では読み手の問いが違う | E2E BDD、業務知識、データ設計へ分ける |
| E2E BDDシナリオにテスト実行記録を混ぜる | 目的達成の共通理解と実行環境の状態では更新理由が違う | E2E BDD資料と検証記録へ分ける |
| RDB論理設計とRDB物理設計を1本にする | 残す論理構造と製品上の実現方法では判断の層が違う | 2つの型へ分ける |
| チュートリアルに設計判断を書く | 学習者は判断材料を持たないので読み飛ばす。文章だけ伸びる | コンセプトへ分けてリンク |
| ハウツーガイドに背景説明を積む | 急いでいる読み手が本題へ辿り着けない | 冒頭1行だけ置き、詳細はリンク |
| コンセプトに手順を書く | 手順は陳腐化が速く、理解の文書ごと腐る | 手順書へ分ける |
| Runbook に「状況に応じて判断」と書く | 判断が要るなら Runbook として失敗している | 分岐を明示するか、ハウツーへ格下げ |
| スタートガイドで網羅する | 最短で動かす目的と衝突する | 最初の一本道だけ書く |
| ADR に実装手順を書く | 決定の記録が実装変更のたびに腐る | 決定と文脈だけ残す |
| ポストモーテムで個人を責める | 事実が出てこなくなり、再発防止に届かない | 仕組みの問題として書く |
| 期間ダイジェストに解説を書く | 追う文書に教える文書が混ざり、一望できなくなる | コンセプトへ分けてリンク |
| 決定ログに述べられていない理由を補う | 補った推測が、後から事実として読まれる | 「言及なし」と書く |
| 論点台帳から取り下げた論点を消す | 同じ論点が数か月後にまた立つ | 取り下げた理由まで残す |
| 実装解説にレビュー意見を混ぜる | 事実と意見の区別が消え、注釈全体が信用されなくなる | 「気になった点」の節へ分ける |
| 実装解説でコードを抜粋する | 省いた部分に何があるか読み手に分からない | 全文を出す |
| コード地図に行番号つきのコードを並べる | 地図の粒度が壊れ、どこへ行くべきか分からなくなる | コードリーディングへ分けてリンク |
| コードリーディングで全文を貼る | 実行順に追う導線が、ファイル順の壁で途切れる | 段階に要る部分を選び、省略に印を置いて原典へ飛ばす |
| コードリーディングの幹へ呼び先の詳細を挟む | 主制御フローを完走する前に別パッケージへ潜り、現在地を失う | 幹は呼び出し契約までにして、詳細は下部の枝へ置き往復リンクする |
| コードリーディングのコードを既定で畳む | 上から読んでコードが1行も現れず、型の目的が達成されない | 本体は開いたまま出す。畳んでよいのは付録だけ |
| コードリーディングを差分の説明にする | 「変更点」と「処理の順」は並べる軸が違い、どちらも中途半端になる | 実装解説（PR）を別に1本立てる |

## 型を宣言する

書き始める前に、本文の冒頭かメタ情報へ明示する。

```
型: ハウツーガイド ／ 読み手: 定期実行ツールを導入済みで、ジョブを追加したい人
```

**読んだ人が「これは自分向けではない」と早く判断できることも成功条件である。**

## 共通の原則（型によらない）

- **読み手はほとんど読まない。** 1ページで読まれるのは多くて3割程度。見出しと最初の数段落で「これは自分に役立つか」に答える。
- **最も重要な情報を冒頭に置く。** ゴールをタイトルに要約し、最初の3段落に要点を入れる。
- **1手順1行動。** 手順に2つの動作を混ぜない。
- **長い塊を割る。** 段落・見出し・リスト・コールアウトで、流し読みできる形にする。
- **1つの文書で狙うゴールは1つ。** 複数の読み手を1本で満たそうとしない。
