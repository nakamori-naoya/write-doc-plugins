# ADR-0007: 重なる利用枠をPostgreSQLの排他制約で防ぐ

> [`adr.md`](../templates/adr.md)の記載例。RoomFlowの制約・候補比較・承認は架空の決定記録であり、実在の承認や性能検証を示さない。PostgreSQLの機能説明は本文の公式資料に基づく。

- **状態**: 承認（この記載例内の状態）
- **決定日**: 2026-08-28
- **決定者**: RoomFlow技術責任者、DB担当（架空の役割）

## 決定

有効な予約が占有する利用枠を`room_booking_claims`へ記録し、同じ拠点・会議室で時間帯が重なる記録を、PostgreSQL 16のGiST排他制約で拒否する。空き状況の事前表示は残し、書込み時の最終的な重複拒否をDBで担う。

対象は仮押さえと確定予約の枠占有である。予約資格や取消権限など、他の業務判断をこの制約へ移す決定ではない。

## なぜ決める必要があったか

同じ部屋へ、ほぼ同時に二件の仮押さえ要求が届く。各要求が「空いている」と読んでから登録するだけでは、両方が同じ空きを見て登録へ進み得る。

また、10:00〜11:30と11:00〜12:00は開始時刻が違っても重なる。開始時刻の一意性では、守りたい「同じ部屋の利用時間帯を重ねない」という条件を表せない。

この例の前提は、枠占有の登録・解除が同じDBへ集まっており、予約の状態変更と占有の変更を一緒に確定できることである。

## 判断基準と比較

優先するのは、同時要求や別の書込経路でも重複を拒否できることと、時間帯の重なりを正しく表せることである。その条件を満たす範囲で、運用する仕組みを増やさない。

| 候補 | 時間帯の重なり | 同時要求への対応 | 採否と理由 |
|---|---|---|---|
| 事前の空き確認だけ | 照会時点では確認できる | 確認後の競合が残る | 不採用。登録時の保証にならない |
| 開始時刻の一意制約 | 開始が違う重なりを表せない | 同じ開始時刻だけ拒否する | 不採用。守る条件が違う |
| 部屋ごとのロックと再確認 | ロック内で確認する | 全経路が同じロックを守る必要がある | 今回は不採用。経路ごとの協調を増やす |
| DBの排他制約 | 同じ部屋と時間範囲の重複を条件にできる | 制約のある書込先で拒否する | 採用。今回の単一DBの境界と合う |

PostgreSQLの[範囲型の制約](https://www.postgresql.org/docs/16/rangetypes.html#RANGETYPES-CONSTRAINT)は、範囲への制約を“non-overlapping”と表現し、同じ部屋の範囲を重複させない例を示している。この機能を枠占有へ適用する。製品の機能があることと、RoomFlowでの実装が正しいことは別に検証する。

## この決定で何が変わるか

同じ部屋に10:00〜11:30の占有があれば、11:00〜12:00の追加は拒否する。11:30〜12:00のように境界で接するだけなら、この重複条件では拒否しない。これは利用範囲の開始を含み、終了を含まない形で記録するためである。

競合時は要求を成功扱いにせず、利用者が別の枠を選べる結果へ変換する。[公式のエラーコード表](https://www.postgresql.org/docs/16/errcodes-appendix.html)では`23P01`を`exclusion_violation`としているため、該当する制約の違反を枠の競合として扱う。

PostgreSQLへの依存と、占有を正しく解除する責務を引き受ける。取消済みなのに占有を残せば空きを塞いでしまうため、取消・期限切れと占有解除の対応も確認する。制約だけで、状態や通知まで正しくなるわけではない。具体的な記録構造は[論理設計](rdb-logical-data-modeling.example.md)を参照する。

## いつ見直すか

一つの部屋を同時に複数顧客へ販売する商品へ変わると、「重なりを一律に拒否する」という基準が変わる。枠占有を複数DBへ分ける場合も、今回の保証の境界を再検討する。

導入前には、重複・隣接・同時要求・取消後の再予約を検証する。負荷時の待ち時間はこの記録では未検証であり、製品機能の説明から推測しない。決定を変えるときは新しいADRを作り、この記録を置換したことを結びつける。
