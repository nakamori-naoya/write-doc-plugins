# よく使う6種類のテンプレート・記載例の改修記録

## 今回の範囲

対象はオンボーディング、ハウツー、チュートリアル、概念説明、ADR、設計提案。利用者の「自分が既存プロジェクトを理解して作業に入る」という回答をオンボーディングへ反映した。ドメイン・データモデルと、今回使わない障害振り返りなどの型は変更していない。

テンプレートだけでなく、対応する記載例と選択時に読むカタログ・型の説明も揃えた。公開する型や依存pluginは増やしていない。

## 何を直したか

| 型 | 元の問題 | 新しい構成が支える理解 |
|---|---|---|
| オンボーディング | 環境構築と30日/90日目標が既定。全体像から最初の変更へつながらない | 役割→一つの処理→読む場所→最初の変更と確認→作業の境界 |
| ハウツー | 前提のない固定時刻・IDを操作指示に使う。受付と完了、結果不明時の扱いが弱い | 開始条件→操作と観測→目的の達成→結果別の次の行動 |
| チュートリアル | APIへの入力が不完全で、提供されていない環境を使う。後始末も削除範囲を断定 | 単体で実行可能な教材→同じ対象の変化→観測の意味→別条件の予測→作ったものだけの後始末 |
| 概念説明 | 意味や関係の説明にも「採らなかった選択肢」を要求する | 定義と関係→同じ場面での働き→理由と境界→答えられる範囲 |
| ADR | 利点・欠点の列挙から何を優先したか読み取りにくい。決定の保証範囲が薄い | 決定→必要になった場面→優先基準と比較→変化・負担・限界→再検討条件 |
| 設計提案 | 同じ期限が10分と15分で矛盾。未計測の数値を観測値のように扱う | 求める判断→目指す結果→代表場面→比較→未決とリスク→試験と停止→判断後の行動 |

## 記載例の読解確認

以下は執筆者自身が、記載例の本文を根拠に行った確認である。独立した読者テストや、実サービスでの効果測定ではない。

| 記載例 | 読み手として試した問い | 本文からの答えと確認した根拠 |
|---|---|---|
| [オンボーディング](../plugins/skills/authoring/content-types/assets/examples/onboarding.example.md) | なぜ取消済みの予約へメールが送られる可能性があるか | 通知の依頼時点と処理時点に時間差がある。「一つの処理を追う」で同じR-101の状態変化を追える |
| 同上 | どこを読んで何を変え、何を確かめるか | 通知の判断箇所と状態読取、対応するテストが問い別の表でつながる。取消済みで送信せず、確定予約では送信する両側を確認する |
| 同上 | この変更で取消と送信の全競合を防げるか | 防げるとは言えない。状態読取後の取消を別の問題として本文に残している |
| [ハウツー](../plugins/skills/authoring/content-types/assets/examples/how-to.example.md) | 画面がタイムアウトしたら新しく予約するか | まず控えた番号で状態を確認する。照会もできなければ新規予約を増やさない |
| 同上 | 09:15は会議の開始時刻か | 違う。9月1日の受付から15分の確定期限であり、9月18日の利用枠と区別している |
| [チュートリアル](../plugins/skills/authoring/content-types/assets/examples/tutorial.example.md) | APIサーバーがなくても体験できるか | 掲載した標準Pythonの教材だけで実行できる。実サービスとの対応範囲と再現しない機能も明示している |
| 同上 | 11時に仮押さえし、11時15分ちょうどに確定するとどうなるか | 期限切れとなる。予測後に掲載コードで実行して確認できる |
| [概念説明](../plugins/skills/authoring/content-types/assets/examples/concept.example.md) | なぜ仮押さえの15分が過ぎても確定予約は残るか | 15分は確定の猶予で、利用枠の長さではない。状態と期限の役割を分けている |
| 同上 | 15分が最適という効果は確認済みか | 確認済みではない。業務上の狙いと実測の有無を区別している |
| [ADR](../plugins/skills/authoring/content-types/assets/examples/adr.example.md) | なぜ事前確認や開始時刻の一意制約では足りないか | 確認後の競合と、開始の異なる重複が残る。重要な判断基準に照らして不採用理由を説明している |
| 同上 | DBを分けても同じ判断を使えるか | 単一DBという前提が変わるため再検討する。制約の保証境界を本文に残している |
| [設計提案](../plugins/skills/authoring/content-types/assets/examples/design-doc.example.md) | 09:08に仮押さえできたら、09:10に消えるか | 消えない。案内の10分は終了し、通常の仮押さえの確定期限は09:23となる |
| 同上 | 合意したらすぐ本番へ入れてよいか | 未決の再案内・希望枠・試験基準を先に確定する。今回はその設計へ進む合意を求めている |
| 同上 | 速く埋めることを優先する場合も同じ案か | 不応答で待ち時間が増えるので、全員通知を再検討する |

- 追加で、期限直前は確定、期限直後は期限切れ、確定後も利用枠が同じであることを確認した。
- 記載例内のローカル資料リンクと、6組のテンプレート・記載例の対応を確認した。
- `bash scripts/validate.sh`は24項目成功・0失敗。配布・設定・工程契約を検証し、`git diff --check`も成功した。文章の意味については上記の自己確認に限る。

RoomFlowの画面、repository、承認や運用を実在として検証したわけではない。各記載例の架空性を明示した。ADRの製品機能だけは、本文へリンクしたPostgreSQL 16の公式資料を確認した。
