# 文書を基準に照らして確かめる

完成文書を読み直し、読み手が目的の説明・判断・行動をできるか評価する。見出しの有無、字数、禁止語の件数による採点で代用しない。別スキルとして呼ばれても、同じ執筆者による確認を独立した読者テストと呼ばない。

## 対象と基準を読む

write-docから保存済みの`path`、`reader_context`、文書型、執筆時の`reader_review`、適用したwriting-rulesの解決済み設定を受け取る。最初に依頼と読者の前提を読み、保存された文書全体を読む。執筆中の確認記録は、自分の評価を作ってから照合し、前の合格判定を引き継がない。

単独使用では指定された文書と依頼から目的・読み手・到達点を整理する。不明な前提は仮定と記す。同梱の[writing-rules](../writing-rules/SKILL.md)の「規律を解決して読む」に従って設定を解決する。write-docから有効な解決済み設定を受け取った場合はそれを使う。呼び出し元のscopeを維持し、解決された規律と[最終確認の基準](../writing-rules/references/final-check.md)を読む。差し替えた規律を同梱の既定に戻さない。

## 読み手の立場で判断する

文書の目的に合う問いを作り、本文のどこを根拠にどう答えられるかを試す。著者だけが知る情報で説明の欠落を埋めない。

- **頭の中に作られる理解**: 対象の役割、要素の関係、条件による変化を説明できるか。これが読み手のメンタルモデルである。未説明の語や視点の切替で、別の理解を作らせていないか。
- **目的への到達**: 説明文なら関係を説明できるか、提案なら採否を根拠付きで判断できるか、手順なら次の操作と完了を見分けられるか。単に情報が載っていることと、使えることを区別する。
- **順序と範囲**: 必要な前提が先に分かり、各論の位置づけを追えるか。枝葉が主題を隠していないか。理解や判断を変える条件まで別文書へ追い出していないか。
- **言葉と具体性**: 日本語の読み手に通じる語か。「エンジニアなら既知」と分野固有の用語を説明なしで使っていないか。具体例があれば概念との対応と限界が分かるか。例やBDDがないことだけで不合格にしない。
- **根拠と表示**: 事実・仮定・提案・未確認を区別できるか。図、表、強調を含めた完成文書で、本文と矛盾した理解を作らないか。HTMLは可能なら表示も確認し、表示を見ていなければその限界を記録する。

規則を説明する文書では条件を一つ変えて適用を試す。手順や参照資料では、その目的に合う操作・検索の問いへ置き換える。すべての文書に同じ問いや一定数の例を要求しない。

## 評価を返す

確認記録には対象の絶対パスと確認した版（ファイルのSHA-256など）、読み手と目的、結論、判断を支える問い・答え・本文の箇所を残す。指摘は「該当箇所→適用した基準→読み手がどう誤解・停滞するか→必要な修正」をつなげる。「分かりにくい」だけや、根拠のない点数で済ませない。

結論は、目的に必要な理解を妨げる不足がなければ「到達点を満たす」、直せる不足なら「要修正」、重要な事実や対象が確認できなければ「判断保留」とする。好みの言い換えは完成を止める理由と区別する。未確認事項が目的の判断を妨げるかも説明する。

単独のレビュー依頼では、本文の変更まで依頼されていなければ指摘を返す。write-docでは修正箇所を執筆・図・保存の担当へ返す。修正後は保存された同じ対象を再読し、指摘の解消と関連する説明の矛盾を確かめ、確認した版と記録を更新する。本文が変わった後に古い確認記録を合格の根拠にしない。

必要な修正が解消された場合だけ`document_review`として確認記録の絶対パスを返し、最終工程を完了する。判断保留や解消できない不足は、残る問いと理由を返して工程を失敗として記録する。記録ファイルの存在は意味の品質を証明しないため、状態管理に任せずこの判断を行う。報告だけを本文へ自動追記しない。

単独使用で自分が規律の設定を解決した場合は、最後にwriting-rulesの設定の後始末を行う。呼び出し元から借りた設定は削除しない。
