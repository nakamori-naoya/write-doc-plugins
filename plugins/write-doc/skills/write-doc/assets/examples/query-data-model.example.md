# クエリデータモデルの見本（抜粋）

この見本は、クエリデータモデルの資料で判断が分かれやすい箇所だけを、図書館の貸出を題材に抜き出したものである。題材の値や言い回しは写さず、どこで何を判断したかを見る。節の構成はテンプレートが持つ。

## 計算から対象を、場面から見せ方を受け取る

業務知識の計算「借りている本」は、確認時点で貸出中か延滞中の本を対象とする。ユーザー目的達成の場面「返す本を確認する」は、返却期限の早い順に、同じ期限なら借りた順に見ることを求める。この二つを根拠に、取得結果を確かめる。

## 必要な事実は、持ち主のテーブルを組み合わせて読む

借りている本を同じ返却期限の中で借りた順に並べるには、借りた時点が要る。`loans` には無いが、`loan_base_events` の借りた事実に `occurred_at` があるので、その行を結び付ける。持ち主のどのテーブルからも導けなかったなら、この資料で作らず、コマンドデータモデルへの差し戻しとして未決に書く。

| 読むテーブル | 持ち主の資料 |
|---|---|
| `loans` | [図書館の貸出のコマンドデータモデル](../貸出/command-data-model.md) |
| `loan_base_events` | [図書館の貸出のコマンドデータモデル](../貸出/command-data-model.md) |

> `loans` から、その利用者の `status` が `lent` か `overdue` の行を選び、`due_on` の昇順に並べる。同じ返却期限なら、`loan_base_events` の `event_type` が `lent` の行を `loan_id` で結び付け、その `occurred_at` の早い順にする。

## 表示順が未決なら、計算から補わない

対象を選ぶ計算があっても、場面にも入出力契約にも表示順が無ければ、表示順は未決である。その答えで取得結果が変わるなら、持ち主へ確認する。業務の計算が対象を定めることと、画面で並びを約束することは別の判断である。

## 「0件が返る」と「拒まれる」を書き分ける

「本の借り手を確認する」場面では、返却済みの貸出しか無い本は空の一覧になる。対象が無い場合に拒むと根拠資料が定めている場合は、取得結果を拒否の規則名の表にする。

| 読み取りの根拠 | この資料のBDD |
|---|---|
