# ユーザー目的達成BDDの見本（抜粋）

この見本は、ユーザー目的達成BDDの資料で判断が分かれやすい箇所だけを、出張手配を題材に抜き出したものである。題材の値や言い回しは写さず、どこで何を判断したかを見る。節の構成はテンプレートが持つ。

## 完了条件は、主たるユーザーが観測できることで書いた

出張者の目的は「訪問予定を守れる移動と宿泊を手配すること」で、手配担当者が確定したことではなく、出張者が確定内容を確認できたときを終わりにした。達成を観測できるのが受け手だけの題材なら、受け手が観測する場面を置き、完了条件を受け手の観測で書く。

> 目的を達したと言えるのは、訪問予定を満たす移動と宿泊の確定内容を、出張者が確認できたときである。

## 失敗の場面は、成功の場面から一条件だけを外して作った

確定の場面と同じ前提から、ホテルを手配できるという条件だけを外した。前提を二つ以上変えると、どの条件で結果が変わったのかが読めなくなるからである。この失敗は目的へ向かう途中で出会うので選び、途中で出会わない障害は場面にしない。

```gherkin
Given: 出張者と手配担当者が候補Aを確定候補として確認している
  And: 候補Aの列車は手配できるが、大阪駅前のホテルは2026年10月13日が満室である
When: 手配担当者が候補Aの移動と宿泊をまとめて確定する
Then: 候補Aの出張手配は確定しない
  And: 出張者が、宿泊を手配できなかったことと、次に候補Bを比較できることを確認できる
  NOTE: Rule: 移動と宿泊は、両方を手配できるときだけまとめて確定する
    Reason: 宿泊を手配できないまま移動だけが確定すると、出張者が帰着期限を満たせないため
```

**接続**: 確定しないまま候補を比較する場面へ戻る。最終地点へは到達していない。

## Whenに立てるのは、出張者とやり取りする役割だけにした

確定の通知を送る仕組みは When に立てず、出張者が確定内容を確認できるという Then の結果として書いた。システムの中で動くものを役割に立てると、主たるユーザーが見て分かる振る舞いから外れるからである。
